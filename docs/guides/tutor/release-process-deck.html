The mental model

One baton: the PR title

The pipeline is a relay with one baton, the PR title. You write it once, for example fix(orchestrator): …. CI checks that it has the right shape. The merge carries it onto main. The release run reads it to decide whether there's a new version and how big the bump is. The annotated git tag then stores it permanently, and the board reads it back out of your checkout's tags. No file stores "the current version": nothing bumps package.json and there's no CHANGELOG. The tag is the record. That's how #295 became v0.3.1 without anyone typing "0.3.1".

A job whose uses: points at another repo's workflow calls a reusable workflow, meaning one declared with on: workflow_call. It runs as if it lived here, using this repo's code and permissions. release-kit's ci-node.yml defines three jobs: checks (install, then each of your commands), pr-title (runs scripts/pr-title.mjs on the title, on PRs only) and skills (a no-op here, since pnpm test already runs that suite). GitHub reports each job as <caller job id> / <called job id>, which is where ci / checks, ci / pr-title and ci / skills come from.

Why do it this way? The dashboard and backlog-manager share one gate. A fix in release-kit, re-tagged as v1, reaches both repos. The obvious beginner move is to copy the YAML into each repo, and the copies would slowly drift apart.

The trade-off. Those three strings are now a contract. The main-pr-only ruleset requires them by exact name. A required check that never reports leaves every PR pending, and the ruleset allows no bypass.

Someone renames the caller job in ci.yml from ci: to gate: while the main-pr-only ruleset is active. What happens to the next PR?

Tempting, but a ruleset matches check names as plain strings. It has no idea which workflow file produced a check, so nothing tells it that gate / checks now stands where ci / checks used to.

ci-node.yml never sees what the caller's job is called. It runs the same three jobs for any job id, so the checks would run and pass, just under different names that nobody requires.

Correct. The checks now report as gate / …. The ruleset keeps waiting for ci / …, which never arrives, and with an empty bypass list nobody can merge past it.

A required check that never reports isn't treated as skipped. Only a job that ran and was skipped reports success. A check that never appears keeps the PR waiting.

Section 1 · The gate

The title rule, and why the title rather than the commits

// release-kit src/conventional.ts:4-6 (@v1)
const RELEASING = /^(feat|fix|perf)(?:\(([a-z0-9-]+)\))?(!)?: (.+)$/;
const SILENT = /^(docs|chore|test|refactor|ci|build)(?:\(([a-z0-9-]+)\))?: (.+)$/;
const SILENT_BREAKING = /^(docs|chore|test|refactor|ci|build)(?:\([a-z0-9-]+\))?!: /;

The releasing types are feat, fix and perf, and they can carry ! for breaking. The silent types are docs, chore, test, refactor, ci and build. They're legal but cut nothing, so chore!: is rejected: a breaking change that never ships has no version for anyone to see. The scope is optional and must be lowercase [a-z0-9-], and an empty description fails.

Why the title? A branch carries "wip" and "address review" commits. A squash merge collapses them into one commit whose subject is the PR title, so the title is the one sentence that survives. Linting every commit message would nag you about history that's about to be thrown away.

The edited trigger (ci.yml:7). Fixing a title re-runs the whole workflow, checks included. If checks were skipped on edits, the skipped job would report success for the same commit, and a red PR would turn green just because it was retitled.

Which title does ci / pr-title reject?

Accepted: perf is a releasing type, so it may carry !. Once merged it cuts a breaking release, which bumps the minor, not the major, while the version is still 0.x.

Correct. ! is allowed only on feat, fix and perf. A breaking chore would be a breaking change that never gets a version, so SILENT_BREAKING rejects it.

Accepted: refactor is a silent type with a lowercase scope. It passes the gate, and when it merges the release run logs that it does not cut a release.

Accepted: the scope is optional, and the description after ": " isn't empty. Merged, this one would cut a patch release from the newest tag.

Questions you might ask

Why does ci / pr-title show green on a push to main?

A push has no PR, so there's no title to check. The job carries if: github.event_name == 'pull_request' (release-kit ci-node.yml:82), and a skipped job reports success. The kit's comment calls this "right here and only here". On a PR, the same skip trick would be the hole the edited trigger exists to close.

Why does ci / skills exist if it does nothing here?

The ruleset in release-kit is shared, so it requires all three checks in every app. This repo passes no skills-command, because pnpm test already runs the node skills suite (scripts/test-all.mjs). The job's Decide step runs and reports green, rather than being absent, which would leave PRs pending (docs/workflows/ci.md:15-16).

Section 2 · The merge

How a commit on main finds its PR

// release-kit src/release.ts:60-66 (@v1, compacted here)
async function findPull(github, cwd, sha) {
  const listed = (await github.pullsForCommit(sha)).find((p) => p.merged && p.mergeCommitSha === sha);
  if (listed) return listed;
  const n = /\(#(\d+)\)$/.exec(await git(cwd, ['log', '-1', '--format=%s', sha]));
  const pull = n ? await github.getPull(Number(n[1])) : null;
  return pull?.merged && pull.mergeCommitSha === sha ? pull : null;
}

After the merge, the engine looks at commits on main, not PRs. For each commit it asks GitHub which PRs contain it, and accepts one only if GitHub recorded this very sha as that PR's merge commit. #295 was squash-merged and landed as one commit, 8efdc26. #291 used "Create a merge commit" and produced f42d720 Merge pull request #291…. Both are their PR's recorded merge commit, so both work. The title comes from the API, not the commit subject: 8efdc26's subject got shortened, yet the tag carries the full title.

What fails: c94807d Merge branch 'main' of …, a local git pull merge pushed straight to main. No PR claims it, so the run logged ::warning::no PR for c94807d… and skipped it. Failing the run instead would let one stray push freeze every later release.

An orchestrator run in merge mode merges item 300, a fix, locally as Merge backlog/300: … and pushes main. What does the next release run do with that commit?

The engine never reads a type from a commit subject, only from the title of the PR it found for that commit. With no PR, there's no title to read, whatever the subject says.

Failing would let one stray push freeze every later release. release.ts:96-100 deliberately warns and moves on, so the commits after it still get released as usual.

The fallback fires only for a subject ending in (#N), and even then the PR must have been merged as this exact sha. Merge backlog/300: … meets neither condition.

Correct. No PR claims the commit, so it gets the warning and is skipped. Its code still ships inside the next tag. It just never gets a version entry or notes of its own.

Section 2 · The merge

The ruleset, and why it isn't on yet

// release-kit rulesets/main.json (@v1, compacted here)
"bypass_actors": [],
"rules": [
  { "type": "pull_request" },              // no direct pushes, 0 approvals needed
  { "type": "required_status_checks",      // the three ci / … contexts,
    "parameters": { "strict_required_status_checks_policy": true } },  // branch up to date
  { "type": "required_linear_history" },   // no merge commits on main
  { "type": "non_fast_forward" }, { "type": "deletion" }
]

scripts/apply-repo-settings.sh futin/backlog-manager applies the ruleset and switches the repo to squash-only merges. Today the repo allows all three merge styles, which is how #291 landed as a merge commit. Squash plus linear history means one PR becomes exactly one commit on main, its subject is the PR title, and findPull always finds a match. A rebase merge would put several commits on main, and all but the last would hit no PR for <sha>.

Why it waits (docs/workflows/ci.md:46-60). In merge mode, the current default, backlog-orchestrate pushes main after every item. Under the ruleset that push is refused and the run parks. So the order is: switch the default to pr mode, prove one PR-mode run, and only then apply the ruleset.

The ruleset is on, and you git push origin main with a docs fix. What happens?

The ruleset guards the branch, not release types. The pull_request rule covers every change to main, whatever its title would have been.

It never gets that far, because the server refuses the push. Even a commit with no PR earns only a warning from the release run, never a failure.

Correct. pull_request means changes reach main only through a PR, and bypass_actors: [] exempts nobody, not even the owner or an admin.

Required checks gate a PR's merge, not a push. With the pull_request rule on, there's no direct-push path for green checks to unlock.

Questions you might ask

Is there any way to push a small docs change straight to main?

Under the shared ruleset, no. The intended route is a quick PR: gh pr create --fill then gh pr merge --squash --auto. Zero approvals are required, so it merges itself once the checks pass (auto-merge has to be enabled for the repo). Adding yourself to bypass_actors works, but it drifts from release-kit's rulesets/main.json, and the orchestrator pushes with your credentials, so it would bypass too. paths-ignore for docs is a trap: the required check never reports.

Why squash-only rather than rebase merges, which also keep history linear?

Both are linear, but a rebase merge puts every branch commit on main. GitHub records only one of them as the PR's merge commit, so findPull (release.ts:60-66) matches that one and logs no PR for <sha> for the rest. Squash gives exactly one commit per PR, whose subject is the title CI already checked.

Section 3 · The release run

What runs, where, and with which token

// .github/workflows/release.yml:7-31 (compacted here)
on: { push: { branches: [main] }, workflow_dispatch: { inputs: { sha: … } } }
permissions: { contents: write, pull-requests: read }
concurrency: { group: release, cancel-in-progress: false }
jobs:
  release:
    uses: futin/release-kit/.github/workflows/release.yml@v1
    with: { sha: ${{ inputs.sha }}, kit-ref: v1 }

The reusable job (release-kit release.yml:31-55) checks out this repo with fetch-depth: 0 (full history and every tag), checks release-kit out into .release-kit/ at kit-ref, sets up Node, sets the tagger to github-actions[bot], and runs node .release-kit/dist/esm/release-cli.js. There's no install step: dist/ is committed to release-kit precisely so that step needs nothing installed.

The token. Every run gets a short-lived GITHUB_TOKEN, passed to the CLI as GH_TOKEN. Listing any permission drops every unlisted one to none. contents: write pushes the tag and creates the Release. pull-requests: read reads PRs. On a public repo like this one PRs are readable anyway. On a private repo the lookup is refused without it.

The order. For each commit: find the PR (release.ts:97), check the title, compute the version, push the tag (:119), create the Release (:120). Cancelling mid-run could leave a tag without its Release, which is why cancel-in-progress is false.

Someone trims release.yml's permissions to contents: write only, on a private repo. A feat PR merges. What does the release run do?

That half-state needs the lookup to succeed first. The lookup runs before the tag push (release.ts:97 vs :119), so the run never gets as far as tagging.

A refused API call isn't "no PR". release-cli.ts:46 throws on any non-zero gh exit, so the run goes red instead of quietly warning and moving on.

Correct. Without pull-requests: read the private repo refuses the PR read, gh exits non-zero, and the run fails before anything has been written.

pull-requests: read is exactly what the PR lookup needs. On a public repo it works by accident, because anyone can read PRs. On a private one the read is refused.

Section 3 · The release run

The range, and the bump

// release-kit src/release.ts:142-153 (@v1, compacted here)
const base = await describeBase(cwd, target);   // newest vX.Y.Z reachable
const range = await git(cwd, ['rev-list', '--first-parent', '--reverse', `${base}..${target}`]);
const commits = [baseCommit, ...range.split('\n')];   // oldest first
for (const sha of commits) outcomes.push(await releaseCommit(cwd, github, log, sha));

A run releases everything since the last tag, one outcome per commit, and one tag per releasing PR. The release group keeps one running run plus one pending run, and a newer push drops the older pending one. That's harmless, because the surviving run sweeps every unreleased commit. Each commit is bumped from the newest tag at that commit (release.ts:113), so a tag made earlier in the same run becomes the next commit's base. The dispatch run after the baseline logged 3553ac7: release-repaired v0.1.0, c7f2d72: released v0.2.0, f42d720: released v0.3.0, 559735f: not-releasing: two new versions, three seconds apart.

Questions you might ask

Why fetch-depth: 0, and not the last tag plus N commits?

git describe walks back from the target to the newest tag, and the distance is unbounded: weeks of silent PRs cut no tag. If the tag falls outside a shallow clone, describe finds no names, which release.ts:27 reads as "no baseline", and the run ends green having released nothing. A wrong N fails silently. Measured here: 982 commits, a 6.3 MiB pack, about 1.4 s to fetch. If that ever grew large, filter: blob:none keeps the whole commit graph and skips file contents.

Why must kit-ref equal the @v1 on uses:?

The workflow file comes from the uses: ref, but the CLI is a second checkout at kit-ref (release-kit release.yml:35-39). If they differed, a workflow from one kit version would run an engine from another, with inputs or env vars they don't agree on. Keeping both at v1 moves them together.

Section 4 · The record

What's inside a tag

// git for-each-ref --format='%(contents)' refs/tags/v0.2.0
feat(releases): version chip and What's new drawer (#290)

- The side rail shows the board's running version; tap it for every release, newest first.

Release-Type: feat
Release-Scope: releases
Release-PR: 290

An annotated tag is a real git object with its own message, author and date. release-kit writes the message in a fixed shape (conventional.ts:75-81): a subject (the PR title plus (#N)), optional notes, and a final paragraph of Release-* trailers, which parseTagMessage (:86-115) reads back. A tag with no Release-Type trailer is the baseline.

The notes are the PR body's ## What's new section, up to the next ## heading, with HTML comments stripped first (extractWhatsNew, :61-69). #290 had that section. #295 had ## Problem and ## Fix but no ## What's new, so v0.3.1 has no notes and its Release page is empty.

Why trailers? They're a git convention a person can read with git show v0.3.1, and the tag can't drift from a second file because there is none. The trade-off: notes are frozen when the tag is cut.

## Why this shape
…

You merge feat(jira): add a JQL filter with the body above. What notes does the tag get?

The heading and the line are in the body, but inside an HTML comment. Comments are stripped before the search runs, so the section counts as missing.

There's no fallback to the lead paragraph or any other part of the body. A missing section means no notes, and the PR title alone becomes the release entry on GitHub.

Notes start only after a ## What's new heading line, and once the comment is stripped that heading no longer exists. Nothing above it is ever collected.

Section 4 · The record

The GitHub Release, and re-runs

The Release is derived from the tag: createRelease (release.ts:81-85) reads the tag message and passes its subject and notes to gh release create --verify-tag. The tag is pushed first, because --verify-tag refuses a tag that origin doesn't have.

Idempotent by construction. Step 1 (:89-94): a commit with its tag and its Release is already-released. A tag with no Release is release-repaired, getting its Release built from the tag and no new tag. Your hand-pushed baseline got its Release exactly that way.

Re-runs: gh workflow run release.yml -f sha=<sha>. The sha must be on main. If a later commit already carries a tag, a dispatch fails with a newer release exists, while a push run ends green: versions are never handed out of order. Tag-first means the only possible half-state is one that step 1 repairs.

A push run pushes v0.4.0, then gh release create hits a GitHub outage and the run goes red. Nothing else merges. You run gh workflow run release.yml. What happens?

That guard looks for tags on a strict descendant of the target. newerRelease skips a tag sitting on the target itself, so v0.4.0 doesn't trip it.

Correct. Step 1 finds v0.4.0 on the commit and no Release. It creates the Release from the tag's own message and pushes no new tag: release-repaired.

Step 1 runs before any bump. A commit that already carries a version tag never reaches the version computation again, so no second number is handed out.

A tag without its Release is the one half-state the design expects, and it's handled automatically. Deleting a pushed version tag is never part of the recovery path.

Questions you might ask

Can I add notes to v0.3.1 after the fact?

On GitHub, yes: edit the Release body by hand. The engine never overwrites an existing Release (createRelease returns early when releaseExists). The board reads the tag message, though (releases.service.ts:124), so the drawer still shows no notes. Changing what the board shows means re-cutting the tag, which rewrites a published ref.

Why are notes written to a temp file, and never passed with -m?

A title or note can hold anything, including backticks or $(…). The engine passes text only as argv elements or files (git tag -F, gh --notes-file, release.ts:68-79), and the workflow never interpolates it into run: through ${{ }} (release-kit release.yml:3-4), so PR text can't become shell code.

On another machine, someone runs git fetch --tags but doesn't pull. HEAD stays on v0.3.0's commit, and the fetch brings in v0.3.1. They reload the board. What do they see?

Section 5 · The board

The drawer and the unseen dot

// client/src/lib/releases.ts:47-53
export function dotState(newest, stored, open) {
  if (!isVersion(newest)) return { dot: false, seed: null };
  if (!isVersion(stored)) return { dot: false, seed: newest };   // first visit
  const above = compareVersions(newest, stored) > 0;
  if (open) return { dot: false, seed: above ? newest : null };  // never lower
  return { dot: above, seed: null };
}

The chip opens the What's new drawer (ReleasesDrawer.tsx). Each entry shows its version, a type badge, a date, the title with its type(scope): prefix removed, the notes as sanitised markdown, and a PR #N link. The baseline is a divider reading "Versioning starts here". The chip carries a dot while there's a release you haven't opened. newest is the drawer's first entry (App.tsx:176), and stored lives in localStorage under backlog-manager.releases-last-seen.

Why localStorage? "Have I seen it" is a per-viewer convenience, not a record. If storage throws, the only effect is no dot. A first visit seeds the stored value silently, so a fresh install doesn't flag every release ever made. Why "never lower" (fix 1908979)? Two checkouts can serve the board at one address. An older board writing its lower version back would flag the releases in between as new all over again.

You open the drawer on main's board, so stored becomes 0.3.1. Later, a worktree board served at the same address, whose newest tag is v0.3.0, has its drawer opened. You go back to main's board. Is there a dot?

That was the behaviour before fix 1908979. Now an open drawer stores the newest version only when it's above the stored one, and 0.3.0 isn't above 0.3.1.

Nothing in dotState ever clears storage. A missing or junk value is re-seeded as a first visit, and that never shows a dot anyway.

Seeding happens only when the stored value is missing or not a version. A valid stored value is left alone on load, and only an open drawer can raise it.

Correct. The worktree's open asked to store nothing, because 0.3.0 isn't above 0.3.1. stored stays at 0.3.1, which matches main's newest.

Questions you might ask

Why doesn't the board poll for new releases?

A version changes only when the server's checkout moves (a merge, then a pull). useReleases (client/src/hooks/useReleases.ts:6-16) reads on mount and each time the drawer opens, never on a timer. A poll would keep asking a question whose answer can't change under an open tab.

Why doesn't the server call release-kit's own readReleases?

readReleases runs git with no timeout, and this server's rule is that every git read goes through runGit, async and bounded at 10 s (releases.service.ts:13-16). So it copies the kit's filters and imports only the pure parseTagMessage. test/api-releases.test.ts checks that both give the same output.
