The mental model

A night-shift worker with a dispatcher

Every half hour a dashboard job wakes a fresh, headless Claude session in one repo and types /backlog-tick. The session doesn't look around and pick something itself. It asks the dispatcher, tick.mjs decide. That's a plain Node script: it reads the backlog, git, the orchestrator's run state and, on a tracker project, the API, then prints one JSON line, the verdict. On most nights most ticks hear "busy" or "idle" and go straight home, at a cost of one tool call and one line. When the verdict is work, it's exactly one unit. Either it executes one ready bug or task into a PR, or it grooms one ungroomed bug or refactor into a plan stamped plan-review for you to approve. The dispatcher hands out that job with a lock on the door. The worker does it, then signs the log with tick.mjs record, which writes down the outcome and takes the lock off. The rest of this deck is about keeping that loop safe with nobody watching:

  • never two workers on one project;
  • never an unreviewed plan executed;
  • never the same impossible item retried every night;
  • a hard stop when a project keeps failing.

1 · One tick, one verdict

A tool decides; the session carries it out

The skill has three steps (SKILL.md:30-90):

  • Decide: run tick.mjs decide, passing the trigger's flags through unchanged.
  • Act: do what the verdict it prints says.
  • Record: run tick.mjs record with the outcome. That writes it to the failure record and releases the lock.

Why split it this way? The spec gives the reason. Putting the decision in a deterministic tool "keeps an idle tick to one tool call and one line of output, and makes the rules testable with node --test beside the tool" (spec:98-99). A schedule may fire every 30 minutes across every pinned repo, so an idle tick has to cost almost nothing.

The beginner's version would let the model read the backlog and choose. That means a full exploration on every tick, and different answers on the same input from one run to the next. The rules would live in prose that no test can pin. Worse, a model weighing an ambiguous case is the one that ends its turn on a question nobody will answer.

The trade-off is duplication. The tool imports nothing from server/, shared/ or another skill's tools/. So every rule it shares with orchestrate.mjs, such as the run-file path and the queue order, is a hand-kept twin whose comment names the original (.claude/rules/skills.md).

// tick.mjs:355-358
  const say = (verdict, reason, extra = {}) => {
    process.stdout.write(`${JSON.stringify({ verdict, reason, ...extra, root, caps, dryRun: opts.dryRun })}\n`);
    return 0;
  };

1 · One tick, one verdict

Five verdicts, and only two take the lock

  • idle: there's nothing to do, or nothing safe to do. Examples: no backlog here, the stack is down, the project is halted, or the queues are empty or capped.
  • busy: someone else is working. That could be another tick, an orchestrator run, a started: marker or a live claim.
  • recover: this tick found a killed tick's lock and cleaned up after it. That cleanup is its one unit.
  • execute / groom: the only verdicts that take the lock. They carry id, skill and args. The session invokes backlog-manager:<skill> with args exactly as printed.

Every line also carries root, caps and dryRun. When dryRun is true, the session runs nothing and records nothing, whatever the verdict (SKILL.md:42-43).

Why does only work take the lock? If an idle or busy tick left a lock, the next tick would read busy: another tick, and a quiet night would keep blocking itself. The alternative, locking at the start of every decide, would turn every crash in the middle of decide into a stale lock that lasts three hours. The trade-off is a gap between reading the world and writing the lock. writeLock covers that gap by refusing to replace a lock that's already there (section 2).

// tick.mjs:465-473 (compacted here)
function act(dir, ctx, base, now, opts, say, unit) {
  if (!opts.dryRun) {
    const lock = { host: os.hostname(), verdict: { kind: unit.kind, id: unit.id }, base: commitOf(ctx.root, base) ?? base, at: new Date(now).toISOString() };
    if (!writeLock(dir, lock)) return say('busy', 'another tick');
  }
  return say(unit.kind, unit.reason, { id: unit.id, skill: unit.skill, args: unit.args });
}

1 · One tick, one verdict

Nobody is there

A tick runs as claude -p with AskUserQuestion disallowed. The skill's rules (SKILL.md:19-28) are about getting through a run with nobody to ask:

  • Never ask. "An unanswered question parks the whole tick." The [backlog-tick] marker at the end of args tells execute and groom the same thing. Wherever they would normally ask, they either decide alone or stop and report (spec:178-182).
  • Never run anything in the background. The process exits when the turn ends, and a background job dies with it.
  • A non-zero exit from decide, record or forget means stop. The stderr line becomes the final message. It is never read as "nothing to do".
  • Quote tracker ids: record '#12' ok …. Without the quotes, the shell reads #12 as a comment.

A beginner's instinct after a failure is to be helpful: retry, wait for the stack, or guess the right id. Each of those either keeps a session hanging with nobody watching or hides a stall. Treating an exit code as "nothing to do" would leave the lock held for the whole TTL, with no line in the run log.

The trade-off is quiet failure. A failed tick ends as an ordinary result and is not escalated: "the run log is the signal, and a push per failed night would be noise" (SKILL.md:100-101). You find out by reading the log or the board's Runs › Ticks page.

Questions you might ask

Why does every verdict carry root?

Step 3 has to run from the main checkout, and the session may no longer be in it. An execute's --finish pr leaves the session's cwd inside .worktrees/execute-<id>. So decide prints the path it resolved, and every step-3 command starts cd '<root>' && (tick.mjs:351-353, SKILL.md:77). The session never has to work out from git where to go back to.

Can I run a tick by hand?

Yes. A typed /backlog-tick in a normal session behaves the same way. --dry-run prints the decision without acting on it: no lock is taken and nothing is recorded (spec:92-94, SKILL.md:42-43). It's the safe way to see what tonight's tick would pick.

Why not just schedule backlog-orchestrate?

Orchestrate drains a whole queue in one long run, and it merges. A tick does one unit and stops at a PR or a plan. It never merges, so backlog-orchestrate stays the only skill that does (spec:16-17, spec:33).

What does a tick do when the pinned repo is a linked worktree?

Nothing: it answers idle: not a main checkout. Execute's pr finish reuses a clean linked worktree on its own branch, so a tick working there would commit and push its work onto your feature branch (spec:88-90).

2 · The idle gate

Cheapest refusal first

cmdDecide is a ladder of early returns (tick.mjs:360-421), and each rung costs more than the one before it:

  1. Not a project → idle. This covers no backlog, not registered, or a linked worktree.
  2. Tracker only: /api/health with a 2 s timeout → idle: stack down. This runs before the lock, because every read and every unit on a tracker project needs the API (tick.mjs:367-368).
  3. The lock: held → busy: another tick; stale → recover (section 5).
  4. The breaker: a halted project → idle, still before any API read (section 5).
  5. Tracker reads: the runs, the items, and the poller's row for this repo.
  6. busyReason.

This order keeps the common case cheap: a halted or locked project costs one call and no network traffic.

The tracker rung has one trap. After a server restart the in-memory tracker cache is empty, so /api/items lists no rows, without any error. Read naively, that looks like "nothing to do". On 2026-10-22 an ixray tick wasted its slot on exactly that false idle (#332). So decide checks with /api/trackers that this repo has actually been polled before it trusts an empty list. The trade-off: a repo with genuinely no issues also gets a slightly alarming reason. That costs nothing, because the verdict is idle either way.

2 · The idle gate

The lock: free, held or stale, made by a link

The lock is one file, ~/.backlog-manager/tick/<project-key>/lock. It holds the host, the verdict that was handed out, the base commit and a timestamp. It holds no pid: decide exits as soon as it prints, so a pid would name a process that's already gone. lockSnapshot reads the lock in one of three states (tick-state.mjs:58-75):

  • free: there's no file;
  • held: the lock is younger than --lock-ttl, 180 minutes by default;
  • stale: the lock is older than that, or the file can't be read or parsed. An unreadable lock is never treated as free. It is "evidence a tick was mid-flight" (tick-state.mjs:46-48).

The interesting part is how writeLock creates it. It writes the bytes to a temp file, then links that file into place. A link fails with EEXIST when the name already exists, so only one of two racing ticks can win. The obvious alternative is to open with 'wx' and then write. That's exclusive too, but it creates the name before the bytes are in it. A second tick reading in that gap would find an empty file, judge it stale and remove it, and then two ticks would run (tick-state.mjs:78-80).

The trade-off: ~/.backlog-manager is local, so the lock only protects one machine. When two machines tick the same tracker project, the claim race at start is the guard, and the tick that loses reports failed (spec:108-109).

// tick-state.mjs:81-97 (compacted here)
export function writeLock(dir, lock) {
  const file = path.join(dir, LOCK_FILE);
  const tmp = tmpPath(file);
  try {
    fs.writeFileSync(tmp, JSON.stringify(lock, null, 2) + '\n');
    try {
      fs.linkSync(tmp, file);
    } catch (e) {
      if (e.code === 'EEXIST') return false;
      throw e;
    }
    return true;
  } finally {
    fs.rmSync(tmp, { force: true });
  }
}

2 · The idle gate

What counts as busy

busyReason returns the first reason that matches, or null (tick.mjs:476-500). The project is busy when any of these holds:

  • the orchestrator's run.json for this project says running or paused. A run file that can't be parsed counts as busy too: it's written atomically, so garbage in it means something needs looking at;
  • a board-started run is in the API's starting list but has no run file yet;
  • tracker: a fresh remote run, another machine, is draining this repo. Between items that run holds no claim, so the claim race alone wouldn't stop a tick (spec:119-121);
  • files: any open item carries a started: marker, in the main checkout or in any linked worktree;
  • tracker: any claim's heartbeat is under 15 minutes old.

The marker scan skips exactly two kinds of tree. One is the orchestrator's .worktrees/<id>, where the run file already speaks for the work. The other is execute's .worktrees/execute-<id>: a killed execute leaves its marker there, and counting it would block the project for good (tick.mjs:502-504). Scanning only the main checkout would be the beginner's mistake, since it misses an in-place groom running in a linked worktree.

The trade-off lands on files projects. A started: marker records when work began, never who started it, and it has no heartbeat. So a marker someone forgot blocks every tick until a person clears it. A Jira session is deliberately not a busy signal: it works on a ticket in its own worktree, not on a backlog item (spec:122).

3 · Choosing the unit

Execute first, under the open-PR cap

Once the gate passes, decide tries execute before groom. That's decision 4 in the spec: execute wins (spec:61). Execute is capped by the number of open execute PRs, meaning open PRs whose head branch starts with execute/, counted once with gh pr list --state open --limit 500. Only while that count is under --max-prs (default 2) does it look for a candidate.

The count deliberately includes PRs from a typed --finish pr run. Those are cut from the same base and conflict the same way, and the cap exists to limit the review pile, whoever made it (spec:125-126). Counting only tick-made PRs would let a busy afternoon of hand runs, plus a night of ticks, build the "morning stack" the spec lists as an anti-goal (spec:52).

Look at what happens when gh can't answer: it's signed out, it fails, or it returns all 500 results. caps.openPrs is null, so execute is treated as capped, with the reason cannot count open PRs. The repo squash-merges, so git alone can't tell whether an execute/ branch was merged (spec:126-127). The tick doesn't stop there. It falls through to groom, carrying that reason. The trade-off: with gh broken, ticks keep grooming and never execute, until someone reads the reason.

3 · Choosing the unit

The execute candidate: listed on disk, read at <base>

On a files project, the candidate scan uses two sources, and either one can rule an item out (tick.mjs:540-562). It lists items from the working tree's open/ directories, and it reads their bytes at <base> through git. To qualify, an item must be:

  • a bug or task, and groomed (derived from its text, the same way the board derives it);
  • committed on <base>: an item with no blob there is skipped;
  • free of plan-review, and on a tracker project free of in-review too;
  • not already taken: no execute/<id> branch and no .worktrees/execute-<id> tree;
  • not skipped by the failure record (section 4).

Why two sources? The bytes come from <base> because execute's worktree is cut from <base>. That way the groomed check, the plan-review check and the hash all describe what execute will actually see. It also means a plan-review line deleted only on disk isn't an approval yet. The listing comes from the working tree because a groom's reject or archive is left uncommitted by design. An item moved out of open/ on disk has been decided against, and a listing at <base> would execute it anyway.

The "not taken" rule exists because a files item stays in open/ until its PR merges. Without that rule, every tick would pick the item already sitting in a PR. The trade-off: when an execute is killed, its leftover branch and worktree keep that item off the list until someone removes them.

// tick.mjs:555-561

    if (isSkipped(state.items[it.id], contentHash(it.text), 'execute')) continue;
    return it;
  }
  return null;

3 · Choosing the unit

The groom candidate, and queue order

When nothing executes, decide grooms, but only while fewer than --max-plans plans are awaiting review (default 3, tick.mjs:448). A plan is awaiting review when its item carries plan-review. Only two kinds of item qualify. An ungroomed bug gets its fix planned. A refactor gets promoted to a planned task. A tick never promotes an idea and never rejects anything: those decisions stay yours (spec:36, spec:64).

On a files project the groom scan reads the working tree, the opposite of execute (tick.mjs:581-598). A tick's groom is left uncommitted by design. A read at <base> would still see last night's bug as ungroomed and groom it a second time. It would also never see last night's plan-review lines, so the plan cap would never fill up.

The args name both the item and the verdict, for example bug-3, plan the fix [backlog-tick] or ref-2, promote it to a task [backlog-tick] (tick.mjs:454). Groom normally states a verdict and waits for you to confirm it. A prompt that already names both counts as that confirmation (spec:173-176).

The order is the orchestrator's. Execute takes bugs, then tasks, oldest first, and puts runner-fix: items ahead of everything, because a runner fix repairs the machinery that later items run on. Groom takes bugs, then refactors, with no hoist: runner-fix is about the order work runs in, and a groom only writes a plan (tick-lib.mjs:162-172).

// tick-lib.mjs:165-172 (compacted here)
export function orderExecute(items) {
  return orderBy(items, ['bugs', 'tasks'], true);
}

export function orderGroom(items) {
  return orderBy(items, ['bugs', 'refactors'], false);
}

4 · The review gate and the failure record

The plan-review mark

A plan written at 3 a.m. by a session nobody watched mustn't be executed until you've read it. The plan-review mark enforces that. On a files project it's a frontmatter line, plan-review: true. On a tracker project it's a label. Groom writes the mark in the same write that lands the plan, through backlog.mjs body|new --plan-review or the frontmatter it prints. So there's never a moment when an approved-looking plan has no mark (spec:146-149). A promote puts the mark on the new task, not on the refactor.

Every execute gate refuses a marked item with the same sentence, this plan awaits review. The gates are the board's Run button, the server's dispatch ladder, the orchestrator's queue, backlog-execute's own refusal and the tick's candidate scan. You approve a plan by removing its mark. On a files project that means deleting the line and committing, because the tick reads the mark at <base>. On a tracker project, you remove the label.

The rejected alternative is on record. The first design said "the uncommitted groom is the gate". That changed because /git-sync commits any uncommitted work, so it would silently approve every tick plan (spec:58-60). The mark is read by presence: any value except false counts, so a hand-typed plan-review: yes still blocks (isMarked, tick-lib.mjs:96). The trade-off is a manual step, since the board has no one-click approve yet (spec:38-39).

4 · The review gate and the failure record

The failure record and its hash

record writes ~/.backlog-manager/tick/<key>/state.json, and tick-state.mjs is the only thing that writes it. The file keeps one entry per item (outcome, kind, reason, time) plus a bounded recent list. A failed entry also stores a contentHash of the item as it stood. As long as the item still hashes to the same value, later ticks skip it. That's the spec's "skip until the item changes" (spec:67-68).

The hash is careful about what counts as a change. It covers the body plus every frontmatter line except the bookkeeping ones: updated, started, phase, groomed-at, and any *-elapsed or *-tokens counter. start and stop rewrite those on every attempt. If they counted, a failed attempt's own bookkeeping would change the hash, and the item would come straight back. On a tracker project the hash covers the issue body, not updated_at, because the tick's own label and comment writes bump updated_at (spec:226-227).

There are two bad alternatives. Retrying every tick burns tokens every night on an impossible item (spec:48). A retry counter has no idea whether anyone fixed the item. The trade-off of the hash: there's no "blocked" outcome. A failure caused by the environment also skips the item until a person runs tick.mjs forget '<id>' (SKILL.md:92-93).

// tick-state.mjs:229-236
const BOOKKEEPING = new Set(['updated', 'started', 'phase', 'groomed-at']);

function isBookkeeping(line) {
  const sep = line.indexOf(':');
  if (sep === -1) return false;
  const key = line.slice(0, sep).trim();
  return BOOKKEEPING.has(key) || key.endsWith('-elapsed') || key.endsWith('-tokens');
}

4 · The review gate and the failure record

Judging ok, and why a failed groom blocks execute

record is only as honest as the outcome the session hands it. So step 3 judges by what the skill left behind, "never from how confident its last sentence sounded" (SKILL.md:61).

  • An execute is ok only if its final message ends with a PR URL on a line of its own.
  • A groom is ok only if the item reads back groomed and marked. For a bug, that means Cause and Fix are filled in and neither says "unknown". For a refactor, it means a promoted task with a plan. The session checks with a read-only backlog.mjs show (SKILL.md:68-75).

A groom wrongly recorded ok causes one of two problems: the bug comes back every tick, still ungroomed, or an unmarked plan gets executed unseen.

That second risk explains an asymmetry in isSkipped. A failure normally skips only the same kind of work, so a failed execute never keeps a later groom away. A failed groom, though, skips execute too. A groom usually fails because its plan read back without the mark, which means the plan has never been reviewed. Executing it on the next tick is exactly what the mark exists to stop.

The trade-off shows on a tracker project. Approving there by removing the label doesn't change the body hash. Once you've reviewed a failed groom's plan, tick.mjs forget '<id>' is the only thing that makes the item eligible again (SKILL.md:94-95).

// tick-state.mjs:259-261
export function isSkipped(rec, currentHash, kind) {
  return rec !== undefined && rec.outcome === 'failed' && (rec.kind === kind || rec.kind === 'groom') && rec.hash !== undefined && rec.hash === currentHash;
}

Questions you might ask

Does a /git-sync commit approve a tick's plan?

No. Committing carries the plan-review: true line onto <base>, and the tick reads the mark at <base>. A plan committed with the line still in it isn't approved (spec:196-198). Approval is deleting the line, then committing that deletion.

Why is there no one-click approve on the board?

It was left out of this version on purpose. You delete the frontmatter line, or remove the label on GitHub or through backlog.mjs. A board control is listed as a follow-up (spec:38-39).

Do groom and execute failures share one record?

Yes. The record holds one entry per item, so the newest outcome, of either kind, is the one consulted (tick-state.mjs:258). For example, a later ok execute replaces an older failed groom.

5 · When a tick dies or keeps failing

A killed tick: claim the stale lock

A dashboard job's timeout: kills a tick mid-work, and so does running out of max-turns. Either way, the lock stays behind. The next tick finds it older than --lock-ttl (180 minutes, well above any sane job timeout) and recovers instead of working (tick.mjs:375-378). That recovery is the tick's one unit.

The tricky part is taking the lock safely. Two ticks can both judge the same lock stale, and a third can write a fresh lock between a judgement and a delete. A blind delete could remove that fresh lock and let two ticks run. So claimStaleLock renames the file to a name only this process uses. A rename of one name has exactly one winner. It then compares the claimed bytes with the bytes it judged stale (tick-state.mjs:121-151):

  • the rename finds nothing → another tick got there first → busy;
  • the bytes differ → it grabbed a fresh lock by mistake, so it links that lock back and answers busy;
  • the bytes match → it owns the recovery.

Next it records the dead verdict's item as failed, with the reason killed at timeout. If that write throws, restoreClaim puts the lock back, so the next tick tries again instead of losing the recovery (tick.mjs:641-653). The trade-off is speed: a killed tick can leave its project doing nothing for up to three hours.

// tick-state.mjs:133-151
export function claimStaleLock(dir, judgedRaw) {
  const file = path.join(dir, LOCK_FILE);
  const claimed = `${file}.recover-${process.pid}-${crypto.randomBytes(4).toString('hex')}`;
  try {
    fs.renameSync(file, claimed);
  } catch (e) {
    if (e.code === 'ENOENT') return null;
    throw e;
  }
  let raw = null;
  try {
    raw = fs.readFileSync(claimed, 'utf8');
  } catch {
    raw = null;
  }
  if (raw === judgedRaw) return claimed;
  restoreClaim(dir, claimed);
  return null;
}

5 · When a tick dies or keeps failing

The only marker a tick clears

On a files project, a killed groom leaves a started: marker on its item, and that marker blocks every later tick (section 2). Someone has to clear it. But a started: marker records only when work began, never who began it, so a tick can't tell whether a person is behind it. That's why recover sets stop: true only when the marker is provably the dead tick's own. That takes three conditions: a files project, a groom verdict in the stale lock, and that item in the main checkout carrying started: together with phase: groom (tick.mjs:636-640). The session then runs backlog.mjs stop '<id>' --abandon on that one id, because the interval was no one's work (spec:163).

Every other case is left alone:

  • a tracker claim goes stale after 15 minutes, and the next claimant's start retires it;
  • an execute's marker lives in .worktrees/execute-<id>, which the busy scan skips. Its branch also keeps the item off the candidate list;
  • any other marker belongs to a person or another session, and it keeps blocking the project.

The bad alternative is "there's a stale lock, so clear whatever markers turn up". That would wipe a person's in-progress groom just because it looked like the dead tick's. The trade-off: a stranded marker from anywhere else needs a person to clear it.

5 · When a tick dies or keeps failing

record's exit 3

record releases the lock only when the lock's verdict id equals the id it was given (tick-state.mjs:101-112). That protects against a tick that outlived its TTL: it must not delete a newer tick's lock. But it also opens a quiet failure. A promote prints a new task id. If the session records that new id instead of the refactor's, the refactor's lock stays held for the whole TTL.

The first version exited 0 in that case. The skill's "non-zero means stop" rule never fired, and nothing reached the run log. Now record exits 3 when the lock names another id (tick.mjs:714-721). The outcome is still written, since it's what the caller saw. The lock stays, since it might belong to a live tick. The skill stops and prints the stderr line. When there's no lock at all, because another tick already recovered it, record exits 0.

That's also why the skill insists that record always takes the verdict's id from step 1, never the new task's (SKILL.md:83-85). It also wants the reason on one line, with each apostrophe written as ’, so a stray single quote can't break the shell command and leave the lock held. The trade-off: record trusts the session to pass the right id, and only catches a wrong one after the fact.

5 · When a tick dies or keeps failing

The breaker

Skipping failed items stops one bad item from taking every night's slot. It doesn't help a project where everything fails, such as one with a broken test suite or a misconfigured repo. The breaker handles that. streakOf walks state.json's recent list newest first and counts consecutive failed entries. It stops at an ok, at an entry stamped at or before the Reset time, or at a timestamp it can't parse (tick-breaker.mjs:82-99). When the streak reaches haltAfter (1–10, default 3, set in settings/tick.json), decide answers idle: halted: … — reset on the board, Runs › Ticks.

Nothing stores "halted". It's derived on every call from recent and the settings, so raising N un-halts the project at the next tick and lowering N halts it. A Reset is a resetAt stamp that the server writes; the tool never writes tick.json. The check sits at step 3b, after the lock and recover steps and before any API read (tick.mjs:380-388). So a halted project still recovers a stale lock, and the check works even with the stack down.

forget leaves recent alone. It's the per-item retry, and Reset is the per-project one (SKILL.md:96). Groom and execute failures count toward the same streak, and so does a recovery's killed at timeout. The trade-off: one bad night can halt a healthy project, and only a person can restart it.

Questions you might ask

What does recover do with a lock it can't read at all?

It claims the lock and drops it, then answers recover with removed an unreadable lock and stop: false. It records nothing, because there's no verdict naming an item (tick.mjs:626-633).

Does a halted project still clean up after a killed tick?

Yes. The lock step runs before the breaker (step 3 before 3b), so a stale lock is still recovered while the project is halted. Its killed at timeout adds one more failure to the streak (tick.mjs:380-383).

Why does the lock store a base commit instead of a branch name?

record and a recovery hash the item's blob at the commit decide read. So an item committed between decide and record can't make a failure look like a failure on the new text (tick.mjs:467-468, tick-state.mjs:41-42).
