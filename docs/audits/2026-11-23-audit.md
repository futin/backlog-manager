## Important findings

Important | runtime | server/src/tracker/github.client.ts:410 | No GitHub call has a deadline. A hung GitHub request stalls the tracker poller, the per-item write chain and the new `POST /api/github/sweep` for minutes. | `request()` calls `this.fetchImpl(url, { method, headers, body })` with no `signal`, no AbortController and no race. Every GitHub REST and GraphQL call goes through this one function, so each is bounded only by undici's default 300 s headers timeout and 300 s body timeout. The Jira and GitLab clients race every call against a 10 s deadline (`JIRA_TIMEOUT_MS`, `GITLAB_TIMEOUT_MS`), but this client does not. Failure path: one stalled socket in a sweep holds the tracker poller's `inFlight`. The sweep is sequential across repos and the next timer is scheduled only at its end, so every repo's `polledAt` freezes. `TrackerPollerService.sweepNow` (`poller.service.ts:490`/`:497`) then awaits that sweep with no bound. A write on the item goes through `GithubSource.writeChain` (`github.source.ts:328`) and blocks every later write to the same item for the same time.

Failure scenario: GitHub accepts a connection and then stalls (a half-open socket, a slow secondary-rate-limit response). The tracker poller's sweep waits up to undici's 300 s defaults on that one call, so every tracker repo's `polled … ago` freezes; a board press of Sync awaits the same sweep with no bound; and every later write to that issue (claim, stop, body edit) queues behind it on the per-item write chain. The same call sits under the orchestrator's tracker heartbeat (runtime Minor at `orchestrate.mjs:5964`), so it can push a `watch` call past the 600 s Bash ceiling. Fix shape: race `fetchImpl` against an `AbortSignal.timeout(...)`, as `jira.client.ts` and `gitlab.client.ts` already do.

Verification: UPHELD — The only GitHub request path, `request()` at github.client.ts:410, calls `this.fetchImpl(url, {method, headers, body})` with no signal, AbortController or race. The client is built in tracker.module.ts:36 as `new GithubClient()`, so it uses plain global `fetch`. No undici `setGlobalDispatcher`, `headersTimeout` or `bodyTimeout` override exists anywhere in server/src. GitLab, by contrast, races every call against `GITLAB_TIMEOUT_MS` (gitlab.client.ts:26/127). In poller.service.ts, `sweep()` (:807) awaits `syncRepo` for each repo in turn and calls `schedule()` only after the loop. `tick()` keeps `inFlight` set until the sweep settles, and `sweepNow` awaits `this.inFlight` (:490) or `tick()` (:497) with no bound. In github.source.ts, `writeChain` (:1274) uses `serialise`, which chains `previous.then(fn, fn)` per URN, so a hung write blocks every later write to that item.

## Refuted

Important | security | server/src/tracker/poller.service.ts:195 | The #341 vetting pin covers only an outsider's issue body, not its title. Refutation: The mechanics are right: `bodyHash` (poller.service.ts:195) hashes only the body, `isUnvetted` (map-issue.ts:145-154) compares only that hash, and `composePrompt` (prompt.util.ts:31) quotes the title. The outsider's original title already goes verbatim through the same `composePrompt` head into the groom session. That session is launched on the unvetted issue (it is the thing that vets it) and is just as able to write files. So a stranger-written title reaching a write-capable session is already possible with no post-groom edit, as the 2026-10-31 refutation said. The claim also does not show that a quoted, at most 256-character label placed before the fixed instruction and the vetted plan actually gets the execute model to act on it. The edit-after-groom path adds no new capability.
