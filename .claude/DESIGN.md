# Design analysis — the board's visual language

Sections 1–7 below are copied verbatim from ../claude-agents-dashboard/.claude/DESIGN.md at commit c179ca4 (2026-09-12) on 2026-09-15; they describe the reference design framework and not this application. Section 8, to follow, documents how this app applies them.

## 1. Typography

### Typeface
A single geometric-grotesque sans is used for everything — UI, labels and numerals. Characteristics visible in the screenshots: tall x-height, closed apertures, straight-cut terminals, circular `o`/`e`, single-story `a`, flat-sided `$`, tabular-feeling lining numerals, slightly condensed caps in the wordmark.

A geometric grotesque in the vein of the Aeonik / Neue Montreal class. Suggested substitutes, in preference order:

```
font-family: "General Sans", "Hanken Grotesk", "Plus Jakarta Sans", Helvetica, sans-serif;
```

No secondary/display face, no serif, no monospace. Numerals are set in the same face as text (not a separate mono) — set `font-variant-numeric: tabular-nums` on all figures and table columns.

### Weights in use
| Weight | Where |
|---|---|
| 400 Regular | body copy, secondary labels, table cells, axis labels |
| 500 Medium | nav items, buttons, card titles, legend labels, tab/chip labels |
| 600–700 Semibold/Bold | big money figures, wordmark, percentages in lists |

Only three weights; nothing lighter than 400, nothing heavier than 700.

### Type scale
| Role | Size | Weight | Line height | Tracking |
|---|---|---|---|---|
| Hero metric (`$12,450`) | 44 px | 700 | 1.05 | −0.02em |
| Large metric (`$15,000`, `$8,450`, `$15,780`) | 30 px | 700 | 1.1 | −0.02em |
| Gauge value (`75%`) | 28 px | 700 | 1.1 | −0.02em |
| Card title (`Monthly spending limit`, `Cost analysis`, `My card`) | 19–20 px | 500 | 1.3 | −0.01em |
| Wordmark | 20 px | 700 | 1 | +0.01em |
| Nav item | 16 px | 500 | 1.4 | 0 |
| Promo heading (`Upgrade to Pro!`) | 20 px | 700 | 1.25 | −0.01em |
| Body / list row (`Housing`, transaction name) | 14–15 px | 400 | 1.45 | 0 |
| Card subtitle (`Balance overview`, `Spending overview`) | 13 px | 400 | 1.4 | 0 |
| Legend, chip label (`7d`, `January`), button label | 13 px | 500 | 1.3 | 0 |
| Meta / axis / tooltip body / date under transaction | 12 px | 400 | 1.35 | 0 |
| Status micro-label (`Completed`, `Declined`), sub-caption (`Left to save 4 months`) | 11 px | 400 | 1.3 | 0 |
| Badge count (`19`) | 11 px | 500 | 1 | 0 |

Pattern: every card uses a **title + one-line subtitle** pair (19/500 over 13/400 grey), then the metric, then the visual. Deltas (`5.1% from last month`) mix two colors in one 12 px line: the number colored, the trailing words grey.

The palette is a three-step warm-to-green ramp; green = positive, orange = spend, yellow = savings.

| Token | Value | Meaning |
|---|---|---|
| `--green-600` | `#5FA92C` | positive delta text, darkest ramp step |
| `--green-500` | `#7DC242` | primary accent green — debit card, filled progress, income bars |
| `--green-400` | `#9BD25C` | gauge mid, ramp step |

Filled bars, the debit card and the gauge all carry a **fine 45° diagonal hatch** (≈2 px stripe, ~8% white over the fill) — the signature texture of the design. Empty/placeholder bars are flat `--bg-track` with no hatch.

Third-party logos in the transaction list keep their own colors on small rounded tiles; everything else stays inside the palette above.

## 3. Spacing

Base unit **4 px**; the layout runs on an 8 px rhythm.

| Token | Value | Use |
|---|---|---|
| `space-1` | 4 px | icon-to-label in dense rows, legend dot gap |
| `space-2` | 8 px | label-to-value, list row gap, chip padding-y |
| `space-3` | 12 px | title-to-subtitle block, inner row padding |
| `space-4` | 16 px | gap between cards in a row/column, nav item padding-x |
| `space-5` | 20 px | card inner padding (small cards) |
| `space-6` | 24 px | card inner padding (standard), app-area padding |
| `space-8` | 32 px | sidebar padding, header-to-first-card |

Measured specifics
- App shell inset from canvas: **≈40 px** all round; shell corner radius 24 px.
- Sidebar width **≈300 px**; content gutter left of cards **24 px**.
- Card grid gutter: **16 px** horizontal and vertical, consistently.
- Card padding: **24 px** on the large ones (balance chart, card widget, transaction history), **20 px** on the short tip/limit cards.
- Header row height **≈56 px**; search field height 48 px; icon buttons 48 × 48 px.
- Nav row height **≈44 px**, 8 px between rows, icon-label gap 12 px. Sub-nav (`History`, `Integration`, `Reports`) indented 36 px with a 1 px L-shaped tree rule.
- Section divider above `Learning center`: 1 px rule with 24 px space above and below.
- Title → subtitle: 4 px. Subtitle → metric: 12–16 px. Metric → chart: 20–24 px.
- List rows (categories, transactions): 26–28 px tall, ~10 px between.
- Quick-action tiles: 48 × 48 px, 12 px gap, label 8 px below.
- Quick-payment avatars: 44 × 44 px, 8 px gap.
- Progress bars: 10 px tall; segmented cost bar 10 px tall with 4 px gaps between segments.
- Spread bar (`ui/SpreadBar`, card scale): 4 px tall, three segments — done `--fill-progress`, in progress `--fill-live`, to do `--ink3` — with 2 px gaps and
  an optional 12 px `--ink3` caption under it; a zero segment is not drawn, and all three at zero draw nothing.

## 4. Radii

| Token | Value | Applied to |
|---|---|---|
| `radius-xs` | 4 px | bar-chart column caps, cost-analysis segments, legend swatches |
| `radius-sm` | 8 px | progress bars (pill-ish at 10 px height), small logo tiles |
| `radius-md` | 12 px | chips (`7d`, `January`), quick-action tiles, avatars, tooltip, badges on avatars |
| `radius-lg` | 16 px | cards, sidebar promo card, debit/credit card faces, search field, header icon buttons, Upgrade button, nav active row |
| `radius-xl` | 24 px | outer app shell |
| `radius-full` | 999 px | notification badge `19`, legend dots, avatar in header |

Nothing is fully square; the smallest radius anywhere is 4 px. Rounding scales with element size — a consistent ratio of roughly 1:8 (radius : shortest side) at the card level.

## 5. Elevation & strokes

- Cards sit on `--bg-app` with a **1 px `--border` stroke and no shadow** (or an imperceptible `0 1px 2px rgba(0,0,0,.03)`).
- Only two things float: the chart **tooltip** (`0 8px 24px rgba(0,0,0,.10)`, white, 12 px radius) and the **app shell** against the grey canvas (`0 24px 64px rgba(0,0,0,.10)`).
- Chart gridlines: 1 px `#EFEFEE`, horizontal only, no vertical lines, no axis line.
- Active nav is marked by a 3 px black bar flush to the left edge of the row plus the `--bg-subtle` fill — not by a color change in the text.
- Drop targets for widgets use a 1 px dashed `--border-strong` outline with 16 px radius.

---

## 6. Iconography

Outline icons, ~1.5 px stroke, 20 px box in nav and 20–22 px in tiles, rounded joins, `--text-primary` color. Chevrons and the `>` in `Read more` are 12–14 px. Icons never take accent color.

---

## 7. Reusable patterns

- **Metric card**: title (19/500) → subtitle (13/400 grey) → figure (30/700) → delta line (12 px, colored number + grey words) → visual.
- **Filter chip**: 13/500 label + chevron, 12 px radius, 1 px `--border-strong`, white fill, sits top-right of the card it filters.
- **Progress row**: name + `current / target` (target in grey), 10 px hatched bar over `--bg-track`, 11 px grey caption under.
- **Two-tone amount**: spent value in `--text-primary`, ceiling in `--text-tertiary`, same size — used for limits and goals alike.
- **Ramp encoding**: category order follows the orange → yellow → green ramp, so the segmented bar and the legend read as one object.

## 8. Applying this to the board

§8 is written new, not copied, for the same reason the dashboard's own §8 is: that section applies §1–7 to sessions, usage, analytics and management — pages this board does not have — and nothing in it draws a kanban column, an item card, a run, a stage track or a watchdog console. What follows is this app's own reading of §§2–6, in the dashboard's register: a number, the rule it sets, then the reason it was set. Two lessons the dashboard's own §8 carries apply to every subsection below, so they are stated once here rather than per subsection: nothing on `--board` uses `--strip-hi` as its only separator — on daylight the two sit two points apart and the element vanishes, which holds for a hover fill too: a control drawn on the board hovers to `--tile-hover` (§8.2) — and a raised control marks a state, never a button.

### 8.0 Shell and rail

The rail is the dashboard's own shipped rail, figure for figure, because the two apps sit in neighbouring tabs and a reader switching between them should see one sidebar rather than two that nearly agree. Until 2026-10-01 this board drew its own 280 px rail with 32/16 padding and an `--ink3` sub-nav, and the first side-by-side read the difference as a bug. Where the dashboard's shipped CSS departs from the spec/mock the two apps share, this board departs with it — recorded here so the next reader does not "correct" either app back to the mock's numbers without the other:

| | Spec / mock | This board | Why |
|---|---|---|---|
| Rail width | 300 px | **240 px**, 24 px above and below and 12 px at the sides, rows 4 px apart, painted `--frame` | the dashboard's shipped rail width (`.rail{flex:0 0 240px}`); this board was 280 px, and that 40 px was the most visible of the differences when switching tabs. The side padding is 12 px since the restyle (spec §4.9) because a row is now a card with a padding of its own. The paper moved with the rows: the rail is grey so the white open row reads as a card on it (decision 63). Since 2026-11-06 the rail and `.maincol` share `--frame`, a step darker than `--board`, so the well is one lighter sheet set into the frame rather than the rail's own grey under a white strip |
| Nav row height | 44 px | **40 px** at least (44 px on the phone menu), around a 28 px `GlyphTile`, 13/500 | the shell mock's row (spec §4.9): a tile and a label rather than an icon and a label. The mock's full 44 px is kept for the phone menu, where the row is a thumb target rather than a pointer one |
| Sub-nav indent | 36 px (the icon's right edge) | **38 px** in from the row's edge: 28 px rows at 12.5/400 `--ink2`, the open page a white `--strip` row at 600 `--ink` | the shell mock's. The white row replaces the old 24 px stem and 12 px tick, so there is no stem to hang from an icon's centreline and the tree is simply indented past the tile; a phone sub-row floors at 40 px. Resting rows beside an `--ink` one would still read as disabled, so the open page is told apart by weight, ink and the white ground together |

The wordmark is a 28 px ink `GlyphTile` (the grid glyph) beside a prompt, in the one face (§1 — no mono): `backlog manager` at 14/700 (`-.01em`) ending in a 7 ×
14 `--green-solid` cursor (1 px radius) 6 px from the word, over an 11/400 uppercase `.rail-kicker` (`.16em` tracking, `--ink3`) that reads `this machine`, 4 px
under it. It was the dashboard's prompt cursor (design handoff "1h") — a `BACKLOG` kicker over a 22/600 `› manager▌` — until the shell restyle (spec §4.9) took
the mock's tile and one-line prompt, and the sub-line now says whose board this is. The cursor is the one part that moves: it blinks (`steps(1)` over 1.06 s) while a run on this machine is working — `runsWorking` (`client/src/lib/run-pulse.ts`): a `starting` entry, or a local run that is `running` and not crashed, never a paused or a remote one — and stands solid otherwise (and before the first answer). It is a hint and never the record; `RunChip` and the Runs page say it in words. `App` reads it from the shell's one runs poll (`OrchestratorRunsProvider`, `useOrchestratorRunsContext().working`), which is `undefined` until the first answer lands and survives a view change. The `<h1>` is named `Backlog Manager` by `aria-label` and its drawn parts are `aria-hidden`. In the phone bar the brand loses its padding and the kicker stays at 11 px — guard 3's floor. Every `<button>` in the rail draws Hanken Grotesk because of one reset rule — `button, input, select, textarea { font-family: inherit; font-variant-numeric: inherit }` — which design guard 2 pins: without it the UA's own `font` shorthand drew every rail row and every card chip in Arial, and that, more than any figure in this table, is why the two rails once looked different.

A row is a 28 px `GlyphTile` and a 13/500 label 10 px apart, with 6 px of padding, a 10 px radius and 40 px at least. At rest the tile is neutral and the label
`--ink2`. The open row is white — `--strip` paper with a faint `--ink` 8 % lift — on the grey `--frame` rail, its tile gone `ink` and its label `--ink` at 600,
so the open section is the one white card in the rail and never a colour change in the label alone (§5). Hover darkens the label and nothing else; the white
fill stays reserved for the open row, so a hovered row and a selected row read as two different things rather than one filled twice. A tile names its section;
the one thing it shows of state is the ink tone of the open row (§6).

The sub-nav tree is drawn only for the open section, as quiet 28 px rows, the open page a white row like the section's own. Runs gets the first one this board has, History, Watchdog and Ticks (§8.4) — the same choice `RUNS_MODE_KEY` (`client/src/lib/runs-mode.ts`) already persists and guards, whose segmented control is replaced by the tree at every width, not only above the phone breakpoint. Settings' Local, Shared and Dashboards (§8.6), Jira's Board, Sessions and Setup (§8.9), Files' Board and Archive and GitHub's Board, Archive and Settings (§8.3, §8.5, §8.6) follow it, one `RailTree` drawing all five, and each tree is its section's page switch — Settings' is the one with a second, in the page's own band (§8.6; spec §3 overrides the old "the rail is the only switch" rule for that page alone).

Since the source-sections change the rail lists five sections — Files, GitHub, Jira, Runs, Settings, in `SECTIONS` order — and draws three of them only when they have something to show: Files and GitHub while a registered project has that source, Jira while `GET /api/jira` says the site is configured (each also while a section the reader chose is being held for its answer; §8.9 for Jira). A machine without Jira credentials or without a GitHub project sees only the rows it can fill, and nothing in the rail moves to make room for an absent one. A load with no stored section, or one that stored the old root Board or Archive, paints the section's loading shape and no source row until the projects answer settles where it lands, so a files-only machine never flashes a GitHub row and board.

**The counts** (restyle spec §4.9; they replace the Needs-you disc of Jira sessions spec §7.4, C4) are one `Pill` each on a row's right end and nowhere else:
amber (`warn`) when the number is people waiting, grey (`neutral`) when it is only a quantity. Jira's counts the sessions that need you — plan, permission,
reply and answer, across every linked ticket, each session once; GitHub's the pull requests that need you (`needsYouCount`, Inbox's Needs-you level), read from
the shell's one `PullRequestsProvider` so it is true on every section and not only while GitHub › PRs is open; Runs' the live runs, grey, from the shell's one
`OrchestratorRunsProvider`. `.rail-count` hangs over the row's right end, 10 px in and vertically centred: every row's button and its count share one
`.rail-group`, the count's positioning parent, with the open tree outside it so the count centres on the row alone; the row is full width. Jira's is a real
`<button>` beside the row's button (a button in a button is invalid) — the row opens Jira, the count opens the Sessions page (§8.9.1) filtered to Needs you with All tickets —
and the other two are plain `role="img"` spans that let the click through to their row. Each is named in words (`4 sessions need you`, `2 PRs need you`, `1 live
run`). Zero draws no element, not an empty pill; while the dashboard is unreachable Jira's keeps the last count rather than showing a false zero.

**The foot.** `.rail-foot`, sunk to the rail's bottom by `margin: auto 0 0`, is a `--strip` card with a hairline border and a 12 px radius holding the version
chip (§8.10) and, at its right, `.rail-api`: an 8 px dot — `--green-solid`, or `--red` when the server is unreachable — and `API connected` or `API unreachable`
at 11 px `--ink3`, from the shell's health read (`App`'s `api`; `null` draws nothing). The card is drawn only while it has either, and in the phone menu it is
the last row, 12 px under the rows.

Settings sits under a 1 px rule with 24 px of air either side: it is about the board, the rows above it — up to four: Files, GitHub, Jira, Runs — are about the work. `.main` sits on `--board` with a 24 px top-left radius — the one corner the rail and the shell strip meet — and no top margin: the strip above it is the gap. The rail and the strip are one `--frame` surface, so the corner is drawn against the frame on both sides.

Below 700 px the rail becomes a top bar, wordmark left and ☰ right, with every tree standing open so a sub-view is a tap away rather than behind an accordion. The bar hides on a downward scroll and returns on the first upward one, and stays pinned while the menu is open, because the menu hangs off it.

**Shell strip.** Right of the rail, `.maincol` stacks a 50 px `.topstrip` over the well on `--frame`, the rail's own token: rail and strip are one frame round the well, and the well's 24 px top-left curve is drawn against it. Decision 63
made the strip `--strip` while the rail was `--board`, and the well — the rail's own grey — met a white band at its corner, which read as a notch (user review,

one token, `--main-gap` (50 px, `0px` on the phone), and design guard 9 pins it. The strip holds what is true of the machine wherever you stand — the
dashboard's rule for its account header — which today is up to two things, right-aligned and 8 px apart: the GitHub status pill and, after it, the Jira one

**The status pills** (restyle spec §4.9a; the Shell mock's top right) are `TrackerChip` for GitHub and `JiraChip` for Jira, one `StatusPill` each: a 28 px chip
of a 7 px dot in the service's tone, the word `GitHub` or `Jira` and, when there is one, how long ago the newest repo or board was polled, inside a bare

### 8.1 Type

| Role | Size / weight | Where |
|---|---|---|
| Page and card title | 19/500, −.01em, 1.3 | band titles, sheet titles, the Runs detail sheet's project |
| Large metric | 30/700, −.02em, 1.1 | figure strip values |
| Row name | 15/500 | column header names |
| Card title | 14/500, 1.35 | item card title, Runs list row project (Live and History), stage track item title |
| Subtitle / hint | 13/400 | band subtitle, sheet subtitle, figure label, control label |
| Body, chip and button label | 13 (500 on buttons) | filter chips, controls |
| Meta / axis / caption | 12/400 | `id · date`, project name beside its dot, stage durations, table time column |
| Pill, badge, status | 11/500 | count pills, markers, mode pill, stage word on the live strip |

11 px is the floor beneath all of these; nothing on the board goes smaller.

Hanken Grotesk is the one face — self-hosted via `@fontsource/hanken-grotesk`, weights 400, 500, 600 and 700 imported in `client/src/main.tsx` — rather than linked the way the dashboard's own foundation links Google Fonts. That is the one place this section departs from the dashboard's: the served build's CSP is `default-src 'self'` with no `font-src`, `style-src` is pinned exactly by `test/csp.test.ts`, and the tailnet/phone use case this board is built for wants no third-party fetch at all.

`--mono` and `--display` are deleted from `theme.css`, not aliased to `--font` — an alias would let a stale `var(--mono)` left behind by the redesign keep quietly resolving to Plex. Deleting it means the same rule instead falls back to the inherited face, which is the failure this board wants to surface rather than hide. `code, kbd, samp, pre { font-family: inherit }` removes the UA's own monospace default for the same reason, so a code span is marked by its fill and ink alone, and `body` carries `font-variant-numeric: tabular-nums` so figures line up wherever they appear. `text-transform: uppercase` survives on `.rail-kicker` alone.

Three faces — Barlow, Barlow Condensed and IBM Plex Mono — left behind 80 `--mono` uses, 14 `--display` uses and 31 `text-transform: uppercase` rules in `client/src/styles.css`, and 124 of that file's 130 `font-size` declarations sat at 12.5 px or smaller. `task-36` cleared all of them: the two tokens and the uppercasing are gone outright (`test/design-guards.test.ts`'s guards 1 and 4 hold them there), and every size below the 11 px floor was raised to the role this table gives it. The sizes at or above 11 px that the table does not name by element were left where they were, because each sits on a surface tasks 2–5 redraw and the primitives those tasks compose carry the full table already.

Every token set as text holds WCAG AA (4.5:1) on all four surfaces, and that is why several values are not the reference palette's. The palette's own `#6e6e6e` / `#a0a0a0` greys and the first daylight status hues — `--green` `#5fa92c` (`--green-600`), `--amber` `#c4761f`, `--mustard` `#9a8712`, `--cyan` `#3f8f14` — measured 2.6–4.35:1 on paper; the values above are the dashboard's AA set, and `test/daylight-contrast.test.ts` recomputes every pair from `shared/theme.css`, the tint sites read off `styles.css` at their own percentage and surface. A second case reads off `styles.css` every token a rule actually sets a word in and holds it to the same line, so a word set in a fill or a mark goes red the day it lands; a rule whose `background` paints something is measured against that ground instead — reverse type on a one-token fill by a third case, words on a tint by the tint case — while `background: none` or `transparent` spares nothing; it spares only a ground it cannot compute (a gradient), the `●` dots and the wordmark's caret (marks drawn as glyphs, closed by selector), and the `--proj-N` identity hues, which are not status colours.

`--tile-hover` is the hover fill of a control drawn straight on `--board`: the Board band's run and plan-review chips, and every `Chip` and `Segmented` a `Band` holds. On the four dark themes it is `--strip-hi`'s own value, lighter than the paper, so the control lifts; on daylight `--strip-hi` sits between the white paper and the grey board, 1.02:1 against the board, and a hovered chip looked transparent, so daylight takes a grey a step below the board. `--strip-hi` keeps every job it has on paper — the rail's active row, popover rows, pressed chips. The shared primitives reach it through a context token, `--hover-fill`: `--strip-hi` on `:root`, re-pointed at `--tile-hover` by `.ui-band` and back by `.ui-popover`, because a `.ui-band .ui-chip:hover` rule would out-specify the chip's own disabled and ink hovers. `test/daylight-contrast.test.ts` holds a hovered control at least as far from the board as a resting one, on every palette.

Marks and text part ways here, under the dashboard's names, so the two repos keep one vocabulary. A status hue is both the ink a word is set in and the fill of a dot, meter, bar or border; on the dark themes one bright value does both, but on paper no green or amber light enough to look like itself clears 4.5:1 as text. So `--green` is the text and `--green-solid` the mark (`--green-500`, the same value as `--fill-progress` — two tokens because they answer different questions; it is 2.2:1 on `--strip`, and every green mark the board draws has its word beside it). Amber's mark is `--amber-solid`, the bright `#c4761f`, 3:1 on every surface a mark sits on. Amber text has no value that is both AA and amber-looking on white, so it takes one of two tokens by what is around it: `--amber-text`, the plain ink, where a neighbouring amber mark or pill already says "warning" (the crashed Live row's line under its `⚠ crashed` pill, the Watchdog card's line holding its attempt pips); `--amber-ink`, a brown `#8a5214`, where the word must carry the hue itself — on an amber tint (the warn pill, the stage chip, the notes and flags) and wherever nothing amber stands beside it (markers, the status word, sheet errors, the degraded-scan line). `--mustard` and `--cyan` stay single tokens, dark enough as text to serve as marks too. The live and paused status words — `running`, `paused`, the Watchdog feed's live kind — read `--live-ink`, `--fill-live`'s text twin: they were set in the fill itself, 2.07:1 on `--strip`, until the branch that made daylight the default. Daylight points it at `--amber-ink` rather than a new brown, so `running` and `aborted` share a colour here exactly as they already do on every dark theme, and the word tells them apart.

On the four dark themes each new token is derived, never declared: a `:root` block in `shared/theme.css`, placed above the daylight block so daylight overrides it, sets `--green-solid` to `var(--green)`, the three amber tokens to `var(--amber)` and `--live-ink` to `var(--fill-live)` — so every dark theme computes exactly what it did before the split. The board's tints keep their own mix per site (6–14 % over `--strip` or `--steel`) rather than a `--X-tint` token per hue as the dashboard has, because one token per hue would move every dark theme's pill fill; each site only mixes the mark token of its hue. `client/src/styles.css` reads bare `var(--amber)` nowhere.

Two tokens are new, added to every theme block, because the design draws two things in the ramp's bright fills and the palette otherwise has no fill that is not also a text colour:

| Token | Meaning | Daylight | Dark themes |
|---|---|---|---|
| `--fill-live` | the card's live strip, the current stage node, the "you are here" bar | `#F5A15C` (`--orange-400`, §2) | `var(--amber)` |
| `--fill-progress` | filled progress, a reached stage node | `#7DC242` (`--green-500`, §2) | `var(--green)` |
| `--on-fill` | ink ON either of those two fills | `var(--ink)` | `var(--on-accent)` |

`--on-fill` is `task-37`'s, added when the card's live strip first set type on one of those fills: `--ink` is right on daylight (`#131313` on `#F5A15C`, 7.3:1) and wrong on the four dark themes, where it is near-white against a bright amber — 1.4:1 on midnight at 11 px. `--on-accent` fails the other way, because on daylight the accents are dark and so that token is white. So the third token is the dark end of whichever palette declares it, and §8.3's "11/500 `--ink` text" is read through it.

Each dark theme block declares its own `var(--amber)` / `var(--green)` line for these rather than sharing one rule across all four, the same way every other ramp token is themed per block. Beyond these two lines, the four dark theme blocks are otherwise unchanged as overrides — no other dark-theme rule in this section is touched.

`.hatch` is one utility rule over any fill: `repeating-linear-gradient(45deg, rgba(255,255,255,.30) 0 1px, transparent 1px 4px)`.

The four column dots read the design's category ramp left to right — refactors `--amber`, ideas `--mustard`, bugs `--red`, tasks `--green` — replacing today's magenta/mustard/red/cyan ticks. The refactors tick is `--magenta`'s last *column* job, but not its last job: the capture dispatch control still reads it. That was four of the token's five uses in the stylesheet — `.dispatch-tab.capture` and `.dispatch-chip.capture`, base and hover — against the tick's one; `task-37` collapsed the control's two shapes into one `Chip` whose action tone paints the WORD, so the four became `.dispatch-word.capture` alone and the tick survived on Archive's own column header until `task-39` put that surface on `BoardColumn` too, which left `.dispatch-word.capture` as the token's one remaining reader. The dispatch chip keeps its three action tones exactly as coded, unchanged by this redesign: groom `--mustard`, execute `--cyan`, capture `--magenta`. Ideas now sharing mustard with the groom chip costs nothing — a column dot and a card's own control are never read as the same object.

The project-hue rule carries over unchanged: one 8 px dot, on the card and on the modal's facts column, never on text — the project name sits in `--ink2` beside it. The eight `--proj-N` sets are themselves untouched; the dot is applied by class, never a `style` attribute, so a theme swap recolours it for free.

The one-home rule for primitives (the design spec's §12.1) applies to every pattern this section draws that more than one surface uses: each is one component in `client/src/components/ui/`, owning one class family in `styles.css`, so two surfaces can never restate — or quietly disagree about — the same look. Until `docs/subsystems/board.md` carries this rule, as the spec's own §11 intends, the spec's §12 table is the pointer for which primitive owns which pattern.

#### 8.4.1 History

**Why the name.** `History` names the rail destination — Runs › History — not the contents of the page under it. That page carries four things and only one of them is past: the figures, the live runs, the past runs, and the selected run whole. It is named for what a person is looking for when they arrive with nothing running, and because a tree whose first leaf repeats its own parent teaches nothing.

**The band.** `Runs` at 19/500 over a 13 px `--ink2` line that counts all three states at once — `3 live · 1 starting · 28 past` — then, right, the project select and the range control as chips. The range control is `RUN_RANGES`' four steps (`client/src/lib/run-range.ts:46`) as one segmented chip, and the sheet subtitles below name whichever is in force.

**The figure strip, directly under the band — the statistics lead.** One sheet the ground divides: five figures on a 2 px `--board` gap grid, wrapping five → three → two under 1100 and under 700 with the seam drawn in both directions, so the gap reads as one grid at every width rather than as five cards that happen to touch. Each cell is a label at 13 `--ink2`, a value at 30/700, and a 12 px line under it. All five carry that line where before this redesign only `runs` and `avg item work` did, and the three new ones say what the figure above them *means* — which is the only thing a line here is allowed to be. The five read what `aggregateRuns` returns (`client/src/lib/run-stats.ts:469`) and nothing else, and that is what rules out the three lines the mock had drawn instead: `+4 vs prior 30 days` compares against a prior period nothing computes, `3 parked` counts something the aggregate does not keep, and `1 red of 41` was invented and in the wrong unit besides.

- **runs** — its line the five-status breakdown, glyph and count each, in `STATUS_ORDER`'s order (`client/src/lib/runs-list.ts`), under a stacked bar (`.runs-status-bar`, `aria-hidden`): one segment per status that has runs, its width that status's share of the runs, toned by `runTone`. The bar is the restyle's (spec §4.6: the tile states a distribution, and a row of five counts makes a reader do the division); it is decoration over the words, which stay, because a tone alone is never the only carrier.
- **completed / queued** — line `merged or branched`, which is the definition of completed rather than a gloss on it.
- **avg item work** — line `queue wait excluded`, the same rule `itemDurationMs` already enforces (`client/src/lib/run-time.ts:401`).
- **rework / completed** — the one-decimal ratio `RunAggregates.fixLoopsPerMerged` (`run-stats.ts:404`) over the line `fix loops per completed item`, with today's long sentence kept as the cell's `title`. The mock's `6 / 41` fraction needs two numbers the aggregate does not return.
- **verify pass** — a rate over verification *runs*, not items, and its line `of every verification run` says which, because the unit is the whole claim.

The wide machine-time tile becomes the strip's **sixth cell, full width**, holding `StageBars` (`client/src/components/runs/StageBars.tsx:42`) redrawn at a 10 px bar height — up from the 6 px `.run-bars-track` shipped before this redesign, because at full width the bar is now the cell's subject rather than a sparkline beside a number. **It is one stacked bar over a legend, not seven one-hue bars** (restyle spec §4.6: seven bars of one hue say how long each stage took but not what share of the machine's time it was). The bar draws a segment only for a stage that recorded time, its width that stage's share, so the widths sum to 100 %; no stage tokens exist and none were added, so the segments use the existing mark tokens — dispatched `--green-solid`, reviewing `--cyan`, fixing `--amber-solid`, verifying `--magenta`, inspecting `--mustard`, preflight and merging `--ink3` — and the legend, which carries the word and the time beside a swatch, is why hue is never the only carrier. The LEGEND is always seven rows, in pipeline order, `—` for a stage never recorded: the seven are `MACHINE_STAGES` (`run-stats.ts:226`), and a stage that drops out when it has no total turns the chart into a different chart per range. Its line is `<range> · queue wait excluded`. The whole strip hides with the list when the range or project filter empties it, as today.

#### 8.4.2 Watchdog

**The band and the status band.** `Runs · Watchdog`, the `section · destination` convention the tree sets, is the `Band`'s title alone. The page's reading is
the **status band** under it (restyle spec §4.7), one `Sheet` row: a ring `GlyphTile` (green while armed), the phase as a word beside a `Dot` (`stateWord`:

as its 13 px sub — `armed — watching <ids>, next check in 42s`, `idle — no running run`, `off — <reason>`, each gaining `· resume disabled` when the switch is
off — the 6 px sweep meter under that while armed, and, right, one flat `Policy in Settings ›` chip: the policy is read here and edited there, and a second
editor for the same three numbers is a second thing to keep in agreement. **The countdown is drawn once**, in that sub and in the one form `next check in 42s`
(numeral and unit with no space): the Sweeper figure's second `next sweep in 4m 12s · every 10m` line is gone with the figure, so the page no longer prints two
countdowns that disagree by a rounding. `checked N s ago` is not served by the API and is not drawn.

**The policy row.** The three figures this page opened on — Sweeper, Watching, Policy — are replaced by the status band above and a policy row BELOW it (restyle
spec §4.7: the user found three numbers inline hard to read, and the other two figures restated what the status band and the Watching sheet's head already say).
The row is a three-cell `FigureStrip` (`watchdog-config-line`): `Check every`, `Leave a resumed run alone` and `Give up after` (`N resumes`), each a label over
a value, with the enabled switch's state as one 12 px line under it. The Sweeper's phase word and its `.hatch` sweep meter (§8.2; a quantity of work, the tick's
own elapsing) moved into the status band; the Watching count is a `Pill` in the Watching sheet's head, and the split the old figure printed — `⚠ 1 crashed · 2
fresh · 1 not yet watched`, the last drawn only when the runs payload is a tick ahead of the sweeper (`WatchdogMonitor.tsx`) — is that head's sub. Those three
words are still the page's own and not a paraphrase of them: what a reader needs is how many runs the sweeper holds an opinion about and how many it does not
yet, and a count this page cannot name is the one thing it must never print. Every policy value is the saved config's, not a constant; their bounds are
`WATCHDOG_LIMITS` (`shared/types.ts:1029`), and the Settings ladders and the server's clamp already read that one triple.

Two switches reach this page and they are not interchangeable, which is why the Policy line names its own — in the mock's words, `resume spawns on · your switch, not the phase`. `WatchdogConfig.enabled` is the user's Settings toggle and withholds the **spawn** alone: a watchdog disabled there still arms, still ticks, and still reports the crashed run it would have resumed. The phase reads `off` only when the environment says so — `offReason()` returns `BM_WATCHDOG off` or `BM_AGENTS off` and nothing else (`server/src/agents/watchdog.service.ts:228-232`, whose own comment records that `enabled` is deliberately not folded in) — and it is that state, an operator's rather than a user's, which hides the Watching sheet below and puts `nothing is watched while off` in this tile.

**The Watching sheet.** Its head is `Watching` with the count as a `Pill`, and the crashed / fresh / not-yet-watched split as its sub; the sheet is omitted while the sweeper is off, the status band having said why. One row per run in the runs payload whose status is `running`, annotated from `watching` exactly as today — skew rendered, not hidden. Each row carries a `Dot`, the project at 14/500, the run id at 12 `--ink3`, `· not yet watched` when the payload is a tick ahead of the sweeper (`client/src/components/runs/WatchdogMonitor.tsx:271`), the verdict as glyph plus word (`● ok` / `⚠ crashed`), `last reported <id> · <stage>` or `between items`, and the heartbeat meter — the age against `RUN_STALE_MS` (`shared/types.ts:767`), amber once past it — under its two labels. A watched id with no run in the payload renders as a placeholder line rather than as nothing: a set the console cannot explain is the failure this page exists to show.

The meter's first label is `heartbeat Ns ago` (`{beat}`, `WatchdogMonitor.tsx:311`) — a numeral every time. Its second label carries none: `stale at <RUN_STALE_MS>` and `past the <RUN_STALE_MS> stale line` are both formatted from the constant at render time (`WatchdogMonitor.tsx:316-318`), and the comment standing beside them gives the reason (`:312-314`): a meter labelled with a typed literal keeps naming the old window the day `RUN_STALE_MS` moves, and on that day the label lies while the meter behind it is still right. The row is a button, and it **jumps to History and selects the run in its detail sheet** — which is what `WatchdogMonitor` does today (`onSelectRun`, `WatchdogMonitor.tsx:79`), and under option D is the only place it could send anyone: the run's detail *is* that sheet.

of its last twelve ticks, the last tick's line and, on a halted project, `Reset`. **The verdict is one pill, `N failures in a row`**: red once the breaker has
halted the project (with the `since <clock> · last: <reason> on <id>` line under it), amber while the streak is still running toward the limit. The separate

is `--red`, anything else is `--hairline2`, and hovering a cell titles it with the clock, kind, id and outcome. The strip is `aria-hidden` with one `sr-only`

#### 8.4.3 The stage track

### 8.8 Motion

Four places on this board move on their own, and one mechanism covers all four rather than four separate ones:

- The **run chip**'s `Dot` (§8.3) breathes a ring while any run is live — `Dot`'s own `breathe?` flag (the design spec's §12.2, per §8.2's one-home rule) rather than an animation local to `RunChip`, so any other live `Dot` on the board earns the same motion for free.
- The **stage track**'s current node (§8.4.3) pulses the 3 px ring already stated there as one of its four node states; this section is where its behaviour under reduced motion is decided, not where its look is drawn a second time.
- A **needs-you control** fades into place rather than snapping in: the crashed run's `Resume run` (§8.4.1's detail sheet head) and the Watchdog page's Resume control (`RunControls`, §8.4.2) are gated by the one function, `watchdogStoodDown`, and mean the same thing wherever they appear — the sweeper has given up and a person is the only path left — so both arrive by fading into a slot the layout already reserves rather than shoving the row beside them.
- The **wordmark's cursor** (§8.0) blinks while a run on this machine is working — `.rail-cursor.blink`, the one class `SideRail` adds from `working`.

All four are silenced under `prefers-reduced-motion: reduce` through the same pattern this codebase already uses, not a mechanism written new for this redesign: a blanket `@media (prefers-reduced-motion: reduce)` rule (`client/src/styles.css:728`) cuts every animation's duration to near zero and runs it once, which freezes it on its LAST keyframe rather than cancelling it — wrong whenever that last frame is not the element's resting state. Three elements already needed the fix for exactly that reason: an explicit `animation: none` after the unconditional rule, in whichever reduced-motion block sits nearest it, carrying `!important` whenever that unconditional rule outranks it on specificity. `.board-card-stage-glyph` is the worked example (`:735`): its unconditional rule is `.board-card-stage .board-card-stage-glyph` (`:464`), two classes deep, so plain source order cannot win and the override needs the flag. `.watchdog-lamp-armed` needs it too, in its own block (`:1443`). `.run-track-dot-current` / `.run-track-node[data-in="live"]` need neither: each shares its selector with its own unconditional rule earlier in the same section, so source order alone settles it (`:2180-2181`). The four this section names carry the same explicit override, each judged per selector: `.ui-dot-breathe` (`:2373`), the stage track's `.run-track-dot-current` (`:2181`), `.run-controls-needs-you` (`:877`) and `.rail-cursor.blink` (beside its own rule in the shell section), none of them needing the flag, because each shares its selector with the unconditional rule it corrects and comes after it — a cursor frozen on `opacity: 0` would read as no wordmark at all. `test/motion-style.test.ts` drives all four from one table, and asserts the glyph's `!important` beside them so that "only where it is needed" stays a judgement rather than a habit. (Every line number here is a pointer, not a contract — they move.)

### 8.9 Jira

The Jira section (Jira phase 2): a rail row between GitHub and Runs, drawn only while `GET /api/jira` says the site is configured, with a Board/Sessions/Setup tree that is its only page switch (§8.0). The picked mocks are `BoardB.html`, `IssueModal.html`, `Setup.html`, `BoardSheet.html`, `NewBoard.html`, `BoardsTen.html` and `Trackers.html` (`docs/superpowers/specs/2026-10-15-jira-mockups/`), and where the spec and a mock differ, the spec wins; the visual overrides are restated in the subsection they touch. Two apply everywhere: the mocks' issue counts are illustrative and were not recomputed, and a path under `$HOME` reads `~` (`displayPath`, from the status's own `home`). **The shared pieces the restyle added** (restyle spec §4.1; Jira rest restyle). A state has one tone and every state-bearing row draws it the same way: `lib/tones.ts` maps a `JiraSessionState` to a `StateTone` (`sessionTone`: `plan`, `permission`, `reply` and `answer` amber; `starting` and `working` green; `quiet` and `ended` grey; `lost` red) and a run's status the same way (`runTone`: `running` green, `paused` amber, `done` and `aborted` grey, `failed` red), so a Sessions row and a Runs card cannot disagree on what amber means, and both functions are exhaustive so a new state is a type error and not a silently grey row. #### 8.9.1 Board

Cards in columns, `BoardB.html`: §8.3's Board read as a Jira board, with the parent as a crumb on the card. Rejected: the roots as groups with their subtasks nested under them (`Main.dc.html`) — the hierarchy took over the column's job, and a column has to say one thing.

**The fold** (`GroupTop.dc.html`, G-A; grouped-board spec §3). Every issue whose parent is on the loaded list folds into its topmost on-board ancestor, at any depth, and only those tops are cards — `foldBoard` in `lib/jira.ts` is the one walk of the parent chain, and a cycle draws its members side by side. It scrolls in the well like Settings and reserves no height, so it reads no strip token (§8.0's `--main-gap` has exactly two readers). Every derivation it prints lives in `client/src/lib/prs.ts`, `lib/pr-run.ts` and `lib/pr-layouts.ts`; `PullRequestsView` and the three layouts (`PrInbox`, `PrMatrix`, `PrCards`) place them and decide nothing. The page draws ONE of three layouts — Inbox, Matrix or Cards — over the same rows, and every layout carries everything the page does (the layouts paragraphs below).

**The band.** `Pull requests` over a live dot and `N open in M repos · polled <age>` (`PrBandSub`; `1 repo` for one) — `N` the sum of each SHOWN repo's `total` (a repo the token cannot read is not counted, see Hidden repos), not of the rows drawn, `M` the shown repos holding at least one open PR, the age the newest shown repo's (`pollAge`, on its own one-second clock; no shown repo read yet, no `· polled …` tail). The dot is the mock's 7 px `--green-solid` span (`.prs-band-dot`), page-local because `Dot` has no such tone and guard 7 forbids restyling it. The layout switch is in the band's trailing slot, right of the title (§ The toolbar and the layout switch); there is no `N open` pill. Until the first answer, and for a server with no token or no registered repo, the sub-line is the static `open pull requests on this machine's GitHub repos` and the slot is empty. Below 700 px the slot wraps under the title at full width and the three buttons share it, so no layout is a sideways scroll away. Before the first answer the page says `loading…`; a failed first read says `pull requests unavailable — <error>`; a failed later read keeps the rows and puts `refresh failed — <error>` above them, because a person part-way through the list should not lose it to one bad poll. A server with no token draws no card at all, only `no token — set BM_GITHUB_TOKEN in .env and restart`: the fix is on the host, so the page says where.

**The toolbar and the layout switch.** The `Segmented` with the `track` skin (`Layout`: `Inbox`, `Matrix`, `Cards`, all three at every width — `PR_LAYOUT_OPTIONS`) sits in the band's trailing slot, not under it (user override, 2026-11-06 — it was a toolbar row under the band; restyle fixes I5; mocks `PRs.dc.html` and `PRsLayouts.dc.html`) — the dashboard's `.seg`, a recessed `--hairline2` ground at 12 px radius under a raised `--strip` option, the ground `FilterBar` draws on the Board's band, and deliberately not §8.6's `pill`: this page is a port of the dashboard's Management pages and its switch reads as theirs. Under the band, the toolbar is a row of 14 px gaps that wraps and holds only the notes: the hidden-repo note when there is one, then, in Cards only, `N repos with no open PRs` (`1 repo with no open PRs`; `emptyRepoNote`, a second `.prs-toolbar-note` after the hidden-repo note or in its place). With neither, the row is not drawn at all. The choice is stored per device (`PR_LAYOUT_KEY`, `usePersistedState`) and read through `parseLayout`, so an unknown stored word is Inbox, the default. Matrix is offered and drawn at every width — on a narrow pane its table scrolls sideways (Matrix, below) rather than the layout vanishing. A switch closes an open merge Confirm. The loading, `no token`, `pull requests unavailable` and `refresh failed` lines sit where the band's paragraph puts them, above or instead of the toolbar.

**Hidden repos and the empty states.** A repo whose last read was `forbidden` or `not-found` is one the token cannot read (`splitReach`, `isNoAccess`, `lib/pr-layouts.ts`): no layout is ever handed it — even if an earlier read left it rows, they are not rows to act on — and the band's `N open in M repos` leaves it out. The toolbar says `N repos hidden — no access · GitHub › Settings`, the last part a `.prs-textlink` button (this page's own text-link look: `.set-link` is §8.6's bordered 36 px row control and reads as a button inside a sentence, so it is not borrowed) calling `onOpenSettings`, the shell's pair threaded down from `App` the way the Sources card's links are, so the rail's tree stays the only page switch; Settings' `Access` card (§8.6) names them and the fix. A rate-limited or generic `error` repo is transient and is NOT hidden: its PRs from the last good read stay ranked and actionable, because a failed refresh is no reason to stop offering a merge, and every layout says it once below the list as `Can't read · <repo> — <detail>` (`access` when the server gave no detail; `PrRepoNotes`, `pr-cantread-<repo>`) — never as a row, since a repo that failed is not a pull request. A hidden repo returns on its own with the next read that answers `ok`. A repo the token reads but whose checks it may not (`PrRepoView.checksDetail`, a GraphQL `FORBIDDEN` on `statusCheckRollup` alone) is NOT hidden: every layout draws its PRs with `checks: 'unknown'` — Quiet on their other facts, a neutral `checks unknown` chip, a Matrix cell reading `unknown` in the `na` tone rather than the `—` that means no checks — and the toolbar says nothing about it, because the sentence and the fix belong on Settings' `Access` card, said once, not on every page that shows the rows. Empty states are checked in this order and are the same in every layout: `no GitHub repo registered` tests the payload's repo list, never the shown one; a payload whose every repo is hidden says `no repo this token can read`; shown repos holding no open PR make the layout say `no open pull requests` once — but only while every shown repo read cleanly, since a rate-limited or errored repo's missing rows are not a read anyone got, so then only its `Can't read` line is drawn. That sentence is distinct from Inbox's `No pull request at this level.`, which only a selected tile can draw.

**The key strip.** `PrActions` (`pr-keys-<key>`, `.prs-keys-side`), the one strip every layout draws, is a **split Merge** and an `Open on GitHub` icon (restyle
spec §4.8). It replaced four outlined `Chip`s — `Merge`, `Auto-merge`, `Update`, `Open ↗` — whose only job was to look like options: four equal outlined chips
on a row is the same too-default problem as `Run ▾` (§11), and Merge is the one action a row is for. `SplitChip` at 28 px: the **main half** does what
`mergeMain` says and nothing else — armed → `Auto-merge on`, enabled, and a click disarms (`enable: false`); checks still running and arming allowed →
`Auto-merge`, which arms with `defaultMethod` rather than offer a merge GitHub would refuse right now; anything else → `Merge`, which opens the row's Confirm in
the foot and never swaps the strip or changes its label. The half is `ink` only when it is `Merge`, unblocked and `primaryKey` names merge (a Quiet, non-draft
PR whose checks are not running); otherwise `outline`, so a PR with a problem has no bright key and the pills, not a button, are where the eye lands. The
**chevron** opens the Merge menu, a `Popover` (`Merge menu`, 280 px) hung from the split's left edge in a Matrix panel (ui-verify D7: right-anchored under a leading-edge split it opened over the rail; the narrow bottom sheet is untouched) of three rows, each a 28 px glyph tile (Merge's green, auto-merge's and Update's neutral, Update drawing the `up` arrow as the mock does, not `refresh` — ui-verify D5; the primary row also rests on the `--strip-hi` ground, `.prs-keys-row-on`, beside its tick — restyle fixes I9, mock `.mi` / `.mi.on`), a label and ONE line on what it does — `Merge` (`asks

merge`), and `Update branch` (`merge <base> into <head>`) — with a tick on the row `primaryKey` picks. The chevron stays enabled while any menu row is allowed,

**Matrix** (`PrMatrix`, at every width). A real `<table>` inside a `.prs-matrix-scroll` box (`overflow-x: auto`, an inline-size container — `Ledger`'s own overflow box cannot be one, since guard 7 forbids a page rule on `.ui-ledger`) inside `Ledger` inside a `Sheet` (`pr-matrix`), at the dashboard Management matrices' geometry — 14 px rows centred on the row, the header in 12/400 `--ink2` over a hairline, the table `max-content` wide with a 100 % minimum so the PR column takes the slack on a wide pane, and the open row on a `--strip-hi` ground with a 3 px inset `--ink` bar, its expansion below the table on the same ground — one row per PR in rank order: a dot, the PR (`#n` link and the title on ONE line with an ellipsis — the full title is its `title` attribute — a `draft` pill, and a sub-line of the short repo name (`repoShortName`) · `head → base` plus the run warning; user override, 2026-11-06: the title wrapped before, and the mock's sub-line is the repo alone — the branches stay, because Matrix's Base column says only `up to date`/`behind`), then Checks, Review, Mergeable, Base, Auto-merge and Updated. Colour is for failure only: a cell's tone is `ok` and `na` in ink, `bad` and `meh` in the needs-you and worth-a-look tones, `live` for in motion (pending, `computing`, `updating…`), and the cell's word is always its text, so colour is never the only carrier; a `bad` or `meh` cell is a `Pill` (`bad`, `warn`) and every other tone is plain text, so the problems are the only filled shapes in the table (restyle spec §4.8). Each header counts the rows whose cell there is `bad` or `meh` (`columnCounts`), the count a `Pill` beside the label. A cell reports its OWN fact whatever the row's level — a draft with failing checks sits among the Quiet rows with a red Checks cell and a counted header, because the dot is the triage and the cells are the evidence; an unnamed `blocked` or `unstable` shows in Mergeable. On a pane narrower than its columns the box scrolls sideways and the table keeps its columns' natural widths: the dot and PR cells are sticky at the box's left edge (`.prs-matrix-sticky`), carrying their row's ground so scrolled cells never show through, and the PR cell's content (`.prs-matrix-pr-inner`) is capped so the two take at most 60 % of the box (`60cqw`), a long title ellipsizing there rather than widening the table. The whole row (`pr-mrow-<key>`, focusable) toggles ONE expansion (`.prs-matrix-panel`, `pr-expand-<key>`), which holds the key strip with its why-line, then the foot. **The panel is not a table row and not the row's next sibling: it renders AFTER the Ledger, as the Ledger's next sibling inside the Sheet** — a rounded `--strip-hi` panel under the table. Two reasons, both load-bearing. The Merge menu is a `Popover`, which portals nothing, and the scroll box's `overflow-x: auto` clips both axes, so a panel inside the table would clip its own menu; outside every overflow box nothing does. And no page selector then has to override a primitive's overflow to un-clip it, which is what guard 7 forbids (`.ui-ledger` is a primitive). It also never scrolls with the table, so `Merge`, `Cancel` and the outcome never sit off-screen. The panel is NOT the failing check names or a `3 of 5 checks` count the mock drew: `PullRequestRow` carries one rolled-up `checks` word and the page polls no per-check read, so there is nothing to list, and the Checks cell's word is the whole reading (restyle spec §4.8). Opening another row replaces it, a click inside an `a`, `button`, `select` or `input` is that control's, and Enter or Space toggles only when the row itself holds focus. Collapsing a row closes the Confirm in it, and the closed expansion is unmounted, for the Escape reason above. A collapsed row's outcome is a pinned row of its own directly under it (`prs-matrix-outcome`); an open row's is the expansion's last line instead. A shown repo with a transient failure is a `Can't read` line below the table, never a row; when no shown repo has a PR and one could not be read, neither the table, its legend nor `no open pull requests` is drawn. A legend (`pr-matrix-legend`) closes the table.

**Cards** (`PrCards`). One `RepoSheet` per repo that holds an open PR or a departed outcome (`cardRepos`), whose anatomy the paragraphs headed `(Cards)` below describe. A repo read cleanly that lists none is not drawn — the toolbar counts it instead (`emptyRepoNote`) — and a repo not yet read is neither drawn nor counted, because unknown is not empty. A repo that could not be read is a `Can't read` line below the cards (`PrRepoNotes part="failures"`), and keeps its card as well while it still holds rows from an earlier read. When neither a card nor a `Can't read` line is drawn, Cards says `no open pull requests` once.

**What every layout carries.** Nothing the cards show is lost in another layout. The run warning is a warn `Pill` in each: at the end of the meta line in Inbox and Cards, on Matrix's sub-line. The key strip (`PrActions`) and the foot (`PrFoot`: the merge Confirm, then `PrOutcomeLine`) are the same two components in each layout, and the foot sits directly under the row's text at the row's full width, never in the keys' column. The outcome of a write that took the PR off the list (`#n merged`) and each sync-off repo's server sentence are drawn once above Inbox's and Matrix's list, and `<repo>: showing n of total` then each `Can't read` line below it (`PrRepoNotes`, `pr-departed-<key>`, `pr-syncoff-<repo>`, `pr-truncated-<repo>`, `pr-cantread-<repo>`); Cards says the first three in each repo's card and draws only the `Can't read` lines below the cards. There is ONE merge Confirm on the page (`confirming`, page state beside the outcomes and marks): `Merge` on a second row moves it there, and the row's write leaving, a layout switch, a read in which its PR is gone or `mergeBlock` refuses it, an Inbox filter that hides the row and collapsing its Matrix row each close it, nothing sent — closed for good, so a PR whose checks recover does not re-open a Confirm nobody asked for. A PR's keys stay disabled in every layout while its write runs: the page holds an in-flight set keyed `<repo>#<number>` and passes it down as `busy`, because a collapse or a layout switch unmounts the strip and with it its own busy state. Outcomes, update marks and their timers are the page's, so switching layout mid-update keeps the mark.

**Grouping (Cards).** One `Sheet` per drawn repo (16 px radius, 24 px padding, `--strip`), flowing two-up in `.prs-cards-grid` (`repeat(auto-fill, minmax(min(520px, 100%), 1fr))`, 16 px gap, top-aligned — one column below ~1100 px of pane, user override, 2026-11-06: it was one column stacked) with the `Can't read` notes under the grid, in `groupRepos` order: repos with open PRs first, the one touched most recently on top, then a repo kept only for a departed outcome, by name; inside a repo the PRs are newest update first. The payload's own order is never what is drawn. A repo is a card of its own, not a kicker over one long list, because what a person can do differs by repo — its merge methods, its auto-merge setting, whether its sync is on — and a card is where that boundary reads.

**The repo heading (Cards).** `SheetHead`, whose title group is a 28 px dark (`ink`) `GlyphTile` with the `branch` glyph, the repo's short name (`repoShortName`: the last `/` segment, the full `owner/name` only when another shown repo shares it) as the 19/500 title, and the neutral `N open` pill right after the name, ahead of any `sync off` pill (restyle spec §4.8); user override, 2026-11-06: the tile was a 32 px checks-tone mark of the repo's worst row, which the mock does not draw — a failing row already says so on its own tile, and the band and Matrix carry the aggregate. The head's right slot, at the trailing edge, carries the readings, 12 px apart: `polled N s ago` (`pollAge`, the same reading the tracker chip and the Jira board use, on a one-second clock of its own so only that span re-renders) and `showing <n> of <total>` when GitHub had more than one page (`truncated`; the page states what it left out rather than paginating). A repo whose sync is off puts a warn `sync off` pill in the head's right slot and the server's full sentence (`repo.syncOff`, `syncOffBlock`'s one home, never a client copy) on a 13 px `--ink2` line under the head, once — readable without hover, because a phone has none. A card never says `no open pull requests` — an empty repo is not drawn — and a repo that could not be read says so in its `Can't read` line below the cards, not in its head. A card kept only for a departed outcome has that outcome as its one line under the head.

**Row anatomy (Cards).** `PrRow`, the one row component Inbox and Cards share, so the two cannot drift: boxless, a hairline between rows, the status tile at the left (above; 28 px here, the layout passes `tileSize`), the key strip at the right with Inbox's wrap rule. Cards passes no `repoLabel`, since the card's head names the repo. The text, top to bottom: `#<n>` in `--ink2` (a link to the PR on github.com, in a new tab with no referrer, underlined on hover) beside the title at 15/500 `--ink`; then one wrapping line (`.prs-line`) of the chips followed by the meta at 13 px `--ink2` — the author (`ghost` for a deleted account) led by a 16 px initials disc (`.prs-av`: one uppercase letter, the login's first character, computed in JS because guard 4 allows one `text-transform` rule; the Jira card's magenta tint on `--strip`, 11 px at 600; `aria-hidden`, the login is written beside it, mock `PRs.dc.html`'s `.av`; ui-verify D3) · `head → base` led by the `branch` glyph (`aria-hidden`, ui-verify D4; Matrix's sub-line draws none) · age, the age because Cards has no Updated column, the run warning at its end; then the foot. The chips (`prPills`) are `Pill`s in `prChips`' reading order — `draft` neutral; `approved` done, `changes requested` bad, `review required` warn; `checks passing` done, `checks failing` bad, `checks pending` warn (each leading with its glyph: tick, cross, clock); `conflicts` bad (leading with a cross); `mergeability pending` neutral, leading with a clock, while GitHub has not computed mergeability (`mergeable: 'unknown'`; the mock's pill, ui-verify D2 — it claims no verdict, only that there is none yet); `behind base` warn; `auto-merge · <method>` done, the tint and not the solid `live` fill — and a repo with no checks draws nothing for them, because a chip claims a fact. `prPills` appends GitHub's own `blocked` / `unstable` word as a warn pill when nothing else names the reason — the one fact the dropped Inbox verdict line carried alone.

**The warning chip.** When something is still working the PR's branch — a live or paused run on this machine or another, a launch pending on another machine, a live claim — `prRunWarning`'s reading (`run in progress on this machine`, `run in progress on <host>`, `launch pending`, `claimed by a live session`) is a warn `Pill`: at the end of the meta line in Inbox and Cards alike (the one `PrRow`), on the sub-line in Matrix. It is a warning and never a refusal: every action keeps exactly the state it would have without it (the spec's "warned about, not refused"). The page derives it from what the Board already polls and adds no request for it.

**Actions and their reasons.** A blocked key — the split Merge's main half, or a Merge-menu row — is `aria-disabled="true"` with a click guard — never the `disabled` attribute, which drops it from the tab order and so from a screen reader's reach — and carries its reason as its `title` and in a visually hidden `aria-describedby` span, `GatedChip`'s pattern (a menu row states it in the place of its line); the span is the key's sibling, because inside the button it would join the key's name. The reasons are `mergeBlock`, `updateBlock` and `autoMergeBlock`, first match wins: `sync off` (the short word on each key of a sync-off repo, since the heading carries the sentence), `updating…` (Update, while the mark is present), `draft`, `not mergeable`, `checks failing`, `no merge method allowed`, `fork does not allow edits`, `no permission to update` (GitHub says the PR cannot be updated while it is behind its base), `already up to date`, `auto-merge not enabled on the repo`. Under the keys the why-line (`.prs-why`, one 12 px `--ink2` line, reasons joined by ` · `; `whyLine`) says the reasons the row does not already show — the repo's and the token's (`REPO_REASONS`: `sync off`, `no merge method allowed`, `auto-merge not enabled on the repo`, `fork does not allow edits`, `no permission to update`) and `updating…` unless the outcome line already says it; a draft, a conflict, failing checks or an up-to-date branch are the row's own facts, on its chips, cells or verdict, so the line does not repeat them. `Merge` asks first through `Confirm`, in the foot — the method `Select` (the repo's `methods`, `defaultMethod` preselected, a stale pick falling back to it) then `Merge #<n> into <base>?`, with a danger `Merge` and a flat `Cancel`, the dismissal focused (§8.4.1's rule); `Confirm` itself is not restyled. The other two menu rows do not ask, because arming is undone by the same key and an update-branch only merges base into head. While a write is in flight both halves of the split Merge are `disabled` outright and its menu closes (the Open icon stays a link) — momentary, with no reason to read — until the page's re-read lands, so a second click cannot send a head SHA the first may already have moved; the write closes the row's Confirm as it leaves.

**The outcome line.** `PrOutcomeLine` (`pr-outcome`, `role="status"`), the foot's last line in every layout, never inside a collapsed part: one 13 px `--ink2` line: `outcomeLine`'s word for a write that stood (`merged`, `already merged`, `auto-merge armed`, `auto-merge off`, `no auto-merge was armed`), `branch updated` for an update that landed, or the server's refusal sentence verbatim in `--red` — a 409's `Head branch was modified…`, a 502's `the token lacks permission for this — …` — never a paraphrase. Every write re-reads afterwards, success or failure. A merge's re-read takes the PR off the open list, so its line moves — to the foot of the repo's card in Cards, above the list in Inbox and Matrix — as `#<n> merged` rather than vanishing with the row that earned it. A PR's line clears the moment its next write leaves, and a repo keeps only its newest three departed lines (`DEPARTED_KEEP`), so a page left open through many writes does not pile them up.

**`updating…`.** GitHub answers update-branch with a 202 and merges later, so the page marks the PR at the head SHA the update was asked from (`UpdateMark`), and the row says `updating…` — its outcome line, and `Update`'s reason — for as long as the mark is present: the mark has no clock of its own, so a render never frees `Update` before a read has judged the update. Any read that shows the head moved drops the mark and says `branch updated`; one that no longer lists the PR drops the mark alone. `UPDATING_MS` (30 s, `shared/types.ts`'s `PR_UPDATING_MS`) after the update the page re-reads once and judges that answer — a new head is `branch updated`, the same head or a failed read drops the mark and its `updating…` — and the server makes the repo due at that same moment, so the re-read is GitHub's answer and not the cache's 60 s TTL. The timer's verdict lands only while the page is mounted. Matrix says `updating…` in the Base cell and only there: an `updating` outcome draws no outcome line in Matrix, open or collapsed, though `Update` still carries it as its reason.
