# Design analysis — the board's visual language

Sections 1–7 below are copied verbatim from ../claude-agents-dashboard/.claude/DESIGN.md at commit c179ca4 (2026-09-12) on 2026-09-15; they describe the reference design framework and not this application. Section 8, to follow, documents how this app applies them.

## 1. Typography

### Typeface
A single geometric-grotesque sans is used for everything — UI, labels and numerals. Characteristics visible in the screenshots: tall x-height, closed apertures, straight-cut terminals, circular `o`/`e`, single-story `a`, flat-sided `$`, tabular-feeling lining numerals, slightly condensed caps in the wordmark.

A geometric grotesque in the vein of the Aeonik / Neue Montreal class. Suggested substitutes, in preference order:

```
font-family: "General Sans", "Hanken Grotesk", "Plus Jakarta Sans", Helvetica, sans-serif;
```

No secondary/display face, no serif, no monospace. Numerals are set in the same face as text (not a separate mono) — set `font-variant-numeric: tabular-nums` on all figures and table columns.

### Weights in use
| Weight | Where |
|---|---|
| 400 Regular | body copy, secondary labels, table cells, axis labels |
| 500 Medium | nav items, buttons, card titles, legend labels, tab/chip labels |
| 600–700 Semibold/Bold | big money figures, wordmark, percentages in lists |

Only three weights; nothing lighter than 400, nothing heavier than 700.

### Type scale
| Role | Size | Weight | Line height | Tracking |
|---|---|---|---|---|
| Hero metric (`$12,450`) | 44 px | 700 | 1.05 | −0.02em |
| Large metric (`$15,000`, `$8,450`, `$15,780`) | 30 px | 700 | 1.1 | −0.02em |
| Gauge value (`75%`) | 28 px | 700 | 1.1 | −0.02em |
| Card title (`Monthly spending limit`, `Cost analysis`, `My card`) | 19–20 px | 500 | 1.3 | −0.01em |
| Wordmark | 20 px | 700 | 1 | +0.01em |
| Nav item | 16 px | 500 | 1.4 | 0 |
| Promo heading (`Upgrade to Pro!`) | 20 px | 700 | 1.25 | −0.01em |
| Body / list row (`Housing`, transaction name) | 14–15 px | 400 | 1.45 | 0 |
| Card subtitle (`Balance overview`, `Spending overview`) | 13 px | 400 | 1.4 | 0 |
| Legend, chip label (`7d`, `January`), button label | 13 px | 500 | 1.3 | 0 |
| Meta / axis / tooltip body / date under transaction | 12 px | 400 | 1.35 | 0 |
| Status micro-label (`Completed`, `Declined`), sub-caption (`Left to save 4 months`) | 11 px | 400 | 1.3 | 0 |
| Badge count (`19`) | 11 px | 500 | 1 | 0 |

Pattern: every card uses a **title + one-line subtitle** pair (19/500 over 13/400 grey), then the metric, then the visual. Deltas (`5.1% from last month`) mix two colors in one 12 px line: the number colored, the trailing words grey.

## 3. Spacing

Base unit **4 px**; the layout runs on an 8 px rhythm.

| Token | Value | Use |
|---|---|---|
| `space-1` | 4 px | icon-to-label in dense rows, legend dot gap |
| `space-2` | 8 px | label-to-value, list row gap, chip padding-y |
| `space-3` | 12 px | title-to-subtitle block, inner row padding |
| `space-4` | 16 px | gap between cards in a row/column, nav item padding-x |
| `space-5` | 20 px | card inner padding (small cards) |
| `space-6` | 24 px | card inner padding (standard), app-area padding |
| `space-8` | 32 px | sidebar padding, header-to-first-card |

Measured specifics
- App shell inset from canvas: **≈40 px** all round; shell corner radius 24 px.
- Sidebar width **≈300 px**; content gutter left of cards **24 px**.
- Card grid gutter: **16 px** horizontal and vertical, consistently.
- Card padding: **24 px** on the large ones (balance chart, card widget, transaction history), **20 px** on the short tip/limit cards.
- Header row height **≈56 px**; search field height 48 px; icon buttons 48 × 48 px.
- Nav row height **≈44 px**, 8 px between rows, icon-label gap 12 px. Sub-nav (`History`, `Integration`, `Reports`) indented 36 px with a 1 px L-shaped tree rule.
- Section divider above `Learning center`: 1 px rule with 24 px space above and below.
- Title → subtitle: 4 px. Subtitle → metric: 12–16 px. Metric → chart: 20–24 px.
- List rows (categories, transactions): 26–28 px tall, ~10 px between.
- Quick-action tiles: 48 × 48 px, 12 px gap, label 8 px below.
- Quick-payment avatars: 44 × 44 px, 8 px gap.
- Progress bars: 10 px tall; segmented cost bar 10 px tall with 4 px gaps between segments.
- Spread bar (`ui/SpreadBar`, card scale): 4 px tall, three segments — done `--fill-progress`, in progress `--fill-live`, to do `--ink3` — with 2 px gaps and
  an optional 12 px `--ink3` caption under it; a zero segment is not drawn, and all three at zero draw nothing.

## 4. Radii

| Token | Value | Applied to |
|---|---|---|
| `radius-xs` | 4 px | bar-chart column caps, cost-analysis segments, legend swatches |
| `radius-sm` | 8 px | progress bars (pill-ish at 10 px height), small logo tiles |
| `radius-md` | 12 px | chips (`7d`, `January`), quick-action tiles, avatars, tooltip, badges on avatars |
| `radius-lg` | 16 px | cards, sidebar promo card, debit/credit card faces, search field, header icon buttons, Upgrade button, nav active row |
| `radius-xl` | 24 px | outer app shell |
| `radius-full` | 999 px | notification badge `19`, legend dots, avatar in header |

Nothing is fully square; the smallest radius anywhere is 4 px. Rounding scales with element size — a consistent ratio of roughly 1:8 (radius : shortest side) at the card level.

## 5. Elevation & strokes

- Cards sit on `--bg-app` with a **1 px `--border` stroke and no shadow** (or an imperceptible `0 1px 2px rgba(0,0,0,.03)`).
- Only two things float: the chart **tooltip** (`0 8px 24px rgba(0,0,0,.10)`, white, 12 px radius) and the **app shell** against the grey canvas (`0 24px 64px rgba(0,0,0,.10)`).
- Chart gridlines: 1 px `#EFEFEE`, horizontal only, no vertical lines, no axis line.
- Active nav is marked by a 3 px black bar flush to the left edge of the row plus the `--bg-subtle` fill — not by a color change in the text.
- Drop targets for widgets use a 1 px dashed `--border-strong` outline with 16 px radius.

---

## 6. Iconography

Outline icons, ~1.5 px stroke, 20 px box in nav and 20–22 px in tiles, rounded joins, `--text-primary` color. Chevrons and the `>` in `Read more` are 12–14 px. Icons never take accent color.

---

## 7. Reusable patterns

- **Metric card**: title (19/500) → subtitle (13/400 grey) → figure (30/700) → delta line (12 px, colored number + grey words) → visual.
- **Filter chip**: 13/500 label + chevron, 12 px radius, 1 px `--border-strong`, white fill, sits top-right of the card it filters.
- **Progress row**: name + `current / target` (target in grey), 10 px hatched bar over `--bg-track`, 11 px grey caption under.
- **Two-tone amount**: spent value in `--text-primary`, ceiling in `--text-tertiary`, same size — used for limits and goals alike.
- **Ramp encoding**: category order follows the orange → yellow → green ramp, so the segmented bar and the legend read as one object.

## 8. Applying this to the board

§8 is written new, not copied, for the same reason the dashboard's own §8 is: that section applies §1–7 to sessions, usage, analytics and management — pages this board does not have — and nothing in it draws a kanban column, an item card, a run, a stage track or a watchdog console. What follows is this app's own reading of §§2–6, in the dashboard's register: a number, the rule it sets, then the reason it was set. Two lessons the dashboard's own §8 carries apply to every subsection below, so they are stated once here rather than per subsection: nothing on `--board` uses `--strip-hi` as its only separator — on daylight the two sit two points apart and the element vanishes — and a raised control marks a state, never a button.

### 8.0 Shell and rail

The rail is the dashboard's own shipped rail, figure for figure, because the two apps sit in neighbouring tabs and a reader switching between them should see one sidebar rather than two that nearly agree. Until 2026-10-01 this board drew its own 280 px rail with 32/16 padding and an `--ink3` sub-nav, and the first side-by-side read the difference as a bug. Where the dashboard's shipped CSS departs from the spec/mock the two apps share, this board departs with it — recorded here so the next reader does not "correct" either app back to the mock's numbers without the other:

| | Spec / mock | This board | Why |
|---|---|---|---|
| Rail width | 300 px | **240 px**, 24 px padding all round, rows 4 px apart | the dashboard's shipped rail (`.rail{flex:0 0 240px;gap:4px;padding:24px}` in its `@media (min-width:640px)` block). This board was 280 px — its own figure between the two — and that 40 px was the most visible of the differences when switching tabs |
| Nav row height | 44 px | **36 px** (44 px on the phone menu) | the dashboard's own rail CSS ships 36 px rows at 14/500 — 8 px shorter than the mock, and lighter than its own DESIGN.md prose still records — and this spec copies the shipped rule rather than the drifted prose; the mock's full 44 px is kept for the phone menu, where the row is a thumb target rather than a pointer one |
| Sub-nav indent | 36 px (the icon's right edge) | **24 px** stem (the icon's centreline: 16 px row padding + half of a 16 px icon), label 20 px past it | the dashboard's: `.rail-sub{margin:2px 0 2px 24px}` hangs the stem, `.rail-sublink{padding:7px 0 7px 20px}` sets the label, and its tick is 12 px in `--hairline2`. Rows are 14/400 `--ink2` at rest and 14/500 `--ink` for the open view — this board's old `--ink3` rows beside an `--ink` one read as disabled rather than as not chosen |

The wordmark is the dashboard's too — its prompt cursor (design handoff "1h"): a `BACKLOG` kicker over `› manager▌`, in the one face (§1 — no mono). The 11/400 uppercase `.rail-kicker` (`.16em` tracking, `--ink3`) sits 4 px over `.rail-prompt` at 22/600 (`-.03em`), whose `›` caret and 10 × 22 cursor (1 px radius) are both `--green-solid`, 8 px from the word, with 24 px of padding under the whole. The cursor is the one part that moves: it blinks (`steps(1)` over 1.06 s) while a run on this machine is working — `runsWorking` (`client/src/lib/run-pulse.ts`): a `starting` entry, or a local run that is `running` and not crashed, never a paused or a remote one — and stands solid otherwise, Settings included. It is a hint and never the record; `RunChip` and the Runs page say it in words. `App` polls nothing for it: Board, Runs and Archive each already run a `useOrchestratorRuns()` and report the answer up (`useReportWorking`), and `App` drops the report on a section change so a view that unmounted cannot keep it blinking. The `<h1>` is named `Backlog Manager` by `aria-label` and its drawn parts are `aria-hidden`. In the phone bar the prompt drops to 17 px with an 8 × 17 cursor 6 px from the word and 3 px under the kicker, which stays at 11 px where the dashboard's bar draws 10 — guard 3's floor. Every `<button>` in the rail draws Hanken Grotesk because of one reset rule — `button, input, select, textarea { font-family: inherit; font-variant-numeric: inherit }` — which design guard 2 pins: without it the UA's own `font` shorthand drew every rail row and every card chip in Arial, and that, more than any figure in this table, is why the two rails looked different.

Rows are 14/500, 16 px padding-x, 16 px radius, a 16 px outline icon 12 px from the label. Active is a 3 px ink bar 16 px tall at the left edge plus a `--strip-hi` fill — never a colour change in the label (§5). Hover darkens the label and nothing else; the fill stays reserved for active, so a hovered row and a selected row read as two different things rather than one filled twice. Icons hold `--ink` at every row weight (§6) — they name the section, never its state.

The sub-nav tree is drawn only for the open section. Runs gets the first one this board has, History, Watchdog and Ticks (§8.4) — the same choice `RUNS_MODE_KEY` (`client/src/lib/runs-mode.ts`) already persists and guards, whose segmented control is replaced by the tree at every width, not only above the phone breakpoint. Settings' Local, Shared and Dashboards (§8.6), Jira's Board and Setup (§8.9), Files' Board and Archive and GitHub's Board, Archive and Settings (§8.3, §8.5, §8.6) follow it, one `RailTree` drawing all five, and each tree is its section's only page switch.

Since the source-sections change the rail lists five sections — Files, GitHub, Jira, Runs, Settings, in `SECTIONS` order — and draws three of them only when they have something to show: Files and GitHub while a registered project has that source, Jira while `GET /api/jira` says the site is configured (each also while a section the reader chose is being held for its answer; §8.9 for Jira). A machine without Jira credentials or without a GitHub project sees only the rows it can fill, and nothing in the rail moves to make room for an absent one. A load with no stored section, or one that stored the old root Board or Archive, paints the section's loading shape and no source row until the projects answer settles where it lands, so a files-only machine never flashes a GitHub row and board.

Settings sits under a 1 px rule with 24 px of air either side: it is about the board, the rows above it — up to four: Files, GitHub, Jira, Runs — are about the work. `.main` sits on `--board` with a 24 px top-left radius — the one corner the rail and the shell strip meet — and no top margin: the strip above it is the gap.

Below 700 px the rail becomes a top bar, wordmark left and ☰ right, with every tree standing open so a sub-view is a tap away rather than behind an accordion. The bar hides on a downward scroll and returns on the first upward one, and stays pinned while the menu is open, because the menu hangs off it.

**Shell strip.** Right of the rail, `.maincol` stacks a 50 px `.topstrip` over the well, both on `--strip` — the rail's own paper, not a new token — so the rail and the strip read as one white L around the `--board` well, and the well's 24 px top-left curve is finally drawn against white (a top margin on `.main` drew it grey on grey, because `body` is `--board` too, and `body` stays so). The strip's height, the well's gap and what `.runs-board` subtracts to fill the viewport are one token, `--main-gap` (50 px, `0px` on the phone), and design guard 9 pins it. The strip holds what is true of the machine wherever you stand — the dashboard's rule for its account header — which today is up to two things, right-aligned: the tracker chip, and since Jira phase 2 the Jira chip after it (§8.9.4), each drawn only while its service is set up; with neither the strip is drawn empty at full height, so the well's top edge never moves.

The tracker chip (`TrackerChip`) is the dashboard's `.acct` pill: a 36 px bare pill, transparent at rest and `--strip-hi` on hover or while open; a 26 px `--strip-hi` avatar with the login's initial (`—` without a token) and a 7 px pip only in two states — `--amber-solid` for no token, `--red` when some repo is failing, nothing when all is healthy; the login at 12.5/600; a `POLL` meter counting down to the server's next sweep (full `--amber-solid` bar reading `overdue` after two silent cycles, full `--red` reading `failing` when every repo fails, empty reading `…` before the first poll); an `API` meter for the hourly budget (`<1%` floor, amber from 60 %, red from 90 %); an 11 px `Chevron` (`client/src/components/ui/Chevron.tsx`) that points `up` while open and `down` otherwise. Both meters are `Meter` (§7's meter row at chip size): label over value, **both 11 px** where the dashboard draws a 9.5 px label and a 9 px caret — guard 3's floor — so the meter is 56 px rather than 52, and it grows to its content rather than wrapping when a value like `overdue` is wider. Its popover is `Popover` (§8.7) at 420 px (`--strip`, a hairline border, 12 px radius, 16 px padding, 8 px below the chip, and the small `0 8px 24px` lift rather than the dialogs' `0 24px 64px`): identity, one row per connected repo with its own 120 px line timer (a failing repo draws a full red bar carrying the access sentence), and the API bar with `N of M left · resets HH:MM`. No links and no buttons in it: the rail is the only thing that switches sections and Settings' pages. Below 700 px the strip is not drawn and the chip sits in the rail bar between the wordmark and ☰ — one element in one home, chosen by `useNarrow` in JS. There it drops the login whenever meters follow it (#229): the 351 px bar has no room for a reading whose width tracks the account, the avatar still carries the initial and the popover the full login, and ☰ is `flex: none` so it never yields its 36 px. The no-token chip keeps its `no token` label — it draws no meters and fits. **Two chips in the bar drop their meters.** When the tracker chip and the Jira chip share the bar, neither draws `.tracker-meters` — avatar, pip and caret only — because with both, even without their logins, the row measured ~178 px over the bar's 351 px content box, and every item but ☰ being `flex: none`, ☰ was pushed past `.rail`'s `overflow-x: hidden` and clipped: the failure #229 fixed for one chip, and the same rule decides it — ☰ is the phone's only section switch and never gives up space. The pip still carries the one reading that must not hide (red, access failing), and each popover prints every meter one tap away. A lone chip keeps its meters, and the desktop strip is outside the rule entirely.

Every disclosure mark is the one `Chevron` (`client/src/components/ui/Chevron.tsx`) — a stroked SVG in `currentColor`, 11 px here (the dashboard's is 9), `dir` `down`, `up` or `right` as rotations of one path, the 160 ms turn off under `prefers-reduced-motion`. Today that is the tracker chip's caret and the dispatch control's mark; `test/chevrons.test.ts` fails any component or `content:` rule that draws a text triangle (`▸ ▾ ▴ ◂ ▶ ▼`) instead.

### 8.1 Type

| Role | Size / weight | Where |
|---|---|---|
| Page and card title | 19/500, −.01em, 1.3 | band titles, sheet titles, the Runs detail sheet's project |
| Large metric | 30/700, −.02em, 1.1 | figure strip values |
| Row name | 15/500 | column header names |
| Card title | 14/500, 1.35 | item card title, Runs list row project (Live and History), stage track item title |
| Subtitle / hint | 13/400 | band subtitle, sheet subtitle, figure label, control label |
| Body, chip and button label | 13 (500 on buttons) | filter chips, controls |
| Meta / axis / caption | 12/400 | `id · date`, project name beside its dot, stage durations, table time column |
| Pill, badge, status | 11/500 | count pills, markers, mode pill, stage word on the live strip |

11 px is the floor beneath all of these; nothing on the board goes smaller.

Hanken Grotesk is the one face — self-hosted via `@fontsource/hanken-grotesk`, weights 400, 500, 600 and 700 imported in `client/src/main.tsx` — rather than linked the way the dashboard's own foundation links Google Fonts. That is the one place this section departs from the dashboard's: the served build's CSP is `default-src 'self'` with no `font-src`, `style-src` is pinned exactly by `test/csp.test.ts`, and the tailnet/phone use case this board is built for wants no third-party fetch at all.

`--mono` and `--display` are deleted from `theme.css`, not aliased to `--font` — an alias would let a stale `var(--mono)` left behind by the redesign keep quietly resolving to Plex. Deleting it means the same rule instead falls back to the inherited face, which is the failure this board wants to surface rather than hide. `code, kbd, samp, pre { font-family: inherit }` removes the UA's own monospace default for the same reason, so a code span is marked by its fill and ink alone, and `body` carries `font-variant-numeric: tabular-nums` so figures line up wherever they appear. `text-transform: uppercase` survives on `.rail-kicker` alone.

Three faces — Barlow, Barlow Condensed and IBM Plex Mono — left behind 80 `--mono` uses, 14 `--display` uses and 31 `text-transform: uppercase` rules in `client/src/styles.css`, and 124 of that file's 130 `font-size` declarations sat at 12.5 px or smaller. `task-36` cleared all of them: the two tokens and the uppercasing are gone outright (`test/design-guards.test.ts`'s guards 1 and 4 hold them there), and every size below the 11 px floor was raised to the role this table gives it. The sizes at or above 11 px that the table does not name by element were left where they were, because each sits on a surface tasks 2–5 redraw and the primitives those tasks compose carry the full table already.

### 8.2 Tokens and themes

`shared/theme.css` keeps its vocabulary; daylight's values are rewritten to the reference palette, the same values the dashboard's own daylight block already carries:

| Token(s) | Daylight |
|---|---|
| `--board` / `--steel` / `--strip` / `--strip-hi` | `#f4f4f3` / `#ededec` / `#ffffff` / `#f2f2f1` |
| `--edge` / `--hairline` / `--hairline2` | `rgba(0,0,0,.03)` / `#eaeae8` / `#dcdcda` |
| `--ink` / `--ink2` / `--ink3` | `#131313` / `#525252` / `#6b6b6b` |
| `--green` / `--amber` / `--mustard` / `--cyan` / `--red` / `--magenta` | `#38631a` / `#c4761f` / `#5f530b` / `#306c0f` / `#b03b28` / `#6b52a8` |
| `--green-solid` / `--amber-solid` / `--amber-text` / `--amber-ink` / `--live-ink` | `#7dc242` / `#c4761f` / `var(--ink)` / `#8a5214` / `var(--amber-ink)` |
| `--on-accent` / `--scrim` / `--shadow` / `--shadow2` | `#ffffff` / `rgba(19,19,19,.28)` / `rgba(0,0,0,.06)` / `rgba(0,0,0,.1)` |

Every token set as text holds WCAG AA (4.5:1) on all four surfaces, and that is why several values are not the reference palette's. The palette's own `#6e6e6e` / `#a0a0a0` greys and the first daylight status hues — `--green` `#5fa92c` (`--green-600`), `--amber` `#c4761f`, `--mustard` `#9a8712`, `--cyan` `#3f8f14` — measured 2.6–4.35:1 on paper; the values above are the dashboard's AA set, and `test/daylight-contrast.test.ts` recomputes every pair from `shared/theme.css`, the tint sites read off `styles.css` at their own percentage and surface. A second case reads off `styles.css` every token a rule actually sets a word in and holds it to the same line, so a word set in a fill or a mark goes red the day it lands; a rule whose `background` paints something is measured against that ground instead — reverse type on a one-token fill by a third case, words on a tint by the tint case — while `background: none` or `transparent` spares nothing; it spares only a ground it cannot compute (a gradient), the `●` dots and the wordmark's caret (marks drawn as glyphs, closed by selector), and the `--proj-N` identity hues, which are not status colours.

Marks and text part ways here, under the dashboard's names, so the two repos keep one vocabulary. A status hue is both the ink a word is set in and the fill of a dot, meter, bar or border; on the dark themes one bright value does both, but on paper no green or amber light enough to look like itself clears 4.5:1 as text. So `--green` is the text and `--green-solid` the mark (`--green-500`, the same value as `--fill-progress` — two tokens because they answer different questions; it is 2.2:1 on `--strip`, and every green mark the board draws has its word beside it). Amber's mark is `--amber-solid`, the bright `#c4761f`, 3:1 on every surface a mark sits on. Amber text has no value that is both AA and amber-looking on white, so it takes one of two tokens by what is around it: `--amber-text`, the plain ink, where a neighbouring amber mark or pill already says "warning" (the crashed Live row's line under its `⚠ crashed` pill, the Watchdog card's line holding its attempt pips); `--amber-ink`, a brown `#8a5214`, where the word must carry the hue itself — on an amber tint (the warn pill, the stage chip, the notes and flags) and wherever nothing amber stands beside it (markers, the status word, sheet errors, the degraded-scan line). `--mustard` and `--cyan` stay single tokens, dark enough as text to serve as marks too. The live and paused status words — `running`, `paused`, the Watchdog feed's live kind — read `--live-ink`, `--fill-live`'s text twin: they were set in the fill itself, 2.07:1 on `--strip`, until the branch that made daylight the default. Daylight points it at `--amber-ink` rather than a new brown, so `running` and `aborted` share a colour here exactly as they already do on every dark theme, and the word tells them apart.

On the four dark themes each new token is derived, never declared: a `:root` block in `shared/theme.css`, placed above the daylight block so daylight overrides it, sets `--green-solid` to `var(--green)`, the three amber tokens to `var(--amber)` and `--live-ink` to `var(--fill-live)` — so every dark theme computes exactly what it did before the split. The board's tints keep their own mix per site (6–14 % over `--strip` or `--steel`) rather than a `--X-tint` token per hue as the dashboard has, because one token per hue would move every dark theme's pill fill; each site only mixes the mark token of its hue. `client/src/styles.css` reads bare `var(--amber)` nowhere.

Two tokens are new, added to every theme block, because the design draws two things in the ramp's bright fills and the palette otherwise has no fill that is not also a text colour:

| Token | Meaning | Daylight | Dark themes |
|---|---|---|---|
| `--fill-live` | the card's live strip, the current stage node, the "you are here" bar | `#F5A15C` (`--orange-400`, §2) | `var(--amber)` |
| `--fill-progress` | filled progress, a reached stage node | `#7DC242` (`--green-500`, §2) | `var(--green)` |
| `--on-fill` | ink ON either of those two fills | `var(--ink)` | `var(--on-accent)` |

`--on-fill` is `task-37`'s, added when the card's live strip first set type on one of those fills: `--ink` is right on daylight (`#131313` on `#F5A15C`, 7.3:1) and wrong on the four dark themes, where it is near-white against a bright amber — 1.4:1 on midnight at 11 px. `--on-accent` fails the other way, because on daylight the accents are dark and so that token is white. So the third token is the dark end of whichever palette declares it, and §8.3's "11/500 `--ink` text" is read through it.

Each dark theme block declares its own `var(--amber)` / `var(--green)` line for these rather than sharing one rule across all four, the same way every other ramp token is themed per block. Beyond these two lines, the four dark theme blocks are otherwise unchanged as overrides — no other dark-theme rule in this section is touched.

`.hatch` is one utility rule over any fill: `repeating-linear-gradient(45deg, rgba(255,255,255,.30) 0 1px, transparent 1px 4px)`.

The four column dots read the design's category ramp left to right — refactors `--amber`, ideas `--mustard`, bugs `--red`, tasks `--green` — replacing today's magenta/mustard/red/cyan ticks. The refactors tick is `--magenta`'s last *column* job, but not its last job: the capture dispatch control still reads it. That was four of the token's five uses in the stylesheet — `.dispatch-tab.capture` and `.dispatch-chip.capture`, base and hover — against the tick's one; `task-37` collapsed the control's two shapes into one `Chip` whose action tone paints the WORD, so the four became `.dispatch-word.capture` alone and the tick survived on Archive's own column header until `task-39` put that surface on `BoardColumn` too, which left `.dispatch-word.capture` as the token's one remaining reader. The dispatch chip keeps its three action tones exactly as coded, unchanged by this redesign: groom `--mustard`, execute `--cyan`, capture `--magenta`. Ideas now sharing mustard with the groom chip costs nothing — a column dot and a card's own control are never read as the same object.

The project-hue rule carries over unchanged: one 8 px dot, on the card and on the modal's facts column, never on text — the project name sits in `--ink2` beside it. The eight `--proj-N` sets are themselves untouched; the dot is applied by class, never a `style` attribute, so a theme swap recolours it for free.

The one-home rule for primitives (the design spec's §12.1) applies to every pattern this section draws that more than one surface uses: each is one component in `client/src/components/ui/`, owning one class family in `styles.css`, so two surfaces can never restate — or quietly disagree about — the same look. Until `docs/subsystems/board.md` carries this rule, as the spec's own §11 intends, the spec's §12 table is the pointer for which primitive owns which pattern.

#### 8.4.1 History

**Why the name.** `History` names the rail destination — Runs › History — not the contents of the page under it. That page carries four things and only one of them is past: the figures, the live runs, the past runs, and the selected run whole. It is named for what a person is looking for when they arrive with nothing running, and because a tree whose first leaf repeats its own parent teaches nothing.

**The band.** `Runs` at 19/500 over a 13 px `--ink2` line that counts all three states at once — `3 live · 1 starting · 28 past` — then, right, the project select and the range control as chips. The range control is `RUN_RANGES`' four steps (`client/src/lib/run-range.ts:46`) as one segmented chip, and the sheet subtitles below name whichever is in force.

**The figure strip, directly under the band — the statistics lead.** One sheet the ground divides: five figures on a 2 px `--board` gap grid, wrapping five → three → two under 1100 and under 700 with the seam drawn in both directions, so the gap reads as one grid at every width rather than as five cards that happen to touch. Each cell is a label at 13 `--ink2`, a value at 30/700, and a 12 px line under it. All five carry that line where before this redesign only `runs` and `avg item work` did, and the three new ones say what the figure above them *means* — which is the only thing a line here is allowed to be. The five read what `aggregateRuns` returns (`client/src/lib/run-stats.ts:469`) and nothing else, and that is what rules out the three lines the mock had drawn instead: `+4 vs prior 30 days` compares against a prior period nothing computes, `3 parked` counts something the aggregate does not keep, and `1 red of 41` was invented and in the wrong unit besides.

- **runs** — its line the five-status breakdown, glyph and count each, in `STATUS_ORDER`'s order (`client/src/lib/runs-list.ts`).
- **completed / queued** — line `merged or branched`, which is the definition of completed rather than a gloss on it.
- **avg item work** — line `queue wait excluded`, the same rule `itemDurationMs` already enforces (`client/src/lib/run-time.ts:401`).
- **rework / completed** — the one-decimal ratio `RunAggregates.fixLoopsPerMerged` (`run-stats.ts:404`) over the line `fix loops per completed item`, with today's long sentence kept as the cell's `title`. The mock's `6 / 41` fraction needs two numbers the aggregate does not return.
- **verify pass** — a rate over verification *runs*, not items, and its line `of every verification run` says which, because the unit is the whole claim.

The wide machine-time tile becomes the strip's **sixth cell, full width**, holding `StageBars` (`client/src/components/runs/StageBars.tsx:42`) redrawn at a 10 px bar height — up from the 6 px `.run-bars-track` shipped before this redesign, because at full width the bar is now the cell's subject rather than a sparkline beside a number. Always seven rows, in pipeline order, `—` for a stage never recorded: the seven are `MACHINE_STAGES` (`run-stats.ts:226`), and a stage that drops out when it has no total turns the chart into a different chart per range. Its line is `<range> · queue wait excluded`. The whole strip hides with the list when the range or project filter empties it, as today.

**The split**, under the strip: a **420 px** list column on the left carrying the Live sheet and then the History sheet, and one detail sheet on the right showing the selected run. Under **1100** px the two columns stack, list first, the detail a scroll away; under **700** px the sheets are full width. 420 px is the figure the row designs below answer to — every reading that does not survive that width is in the detail sheet instead, and the list is what has to stay legible when the detail is a scroll away.

**Wide** (2026-09-17): once the BOARD is **1400 px** or wider, the page becomes three columns — the band spanning the top, the split holding the first column exactly as above, and the figure strip leaving the top of the page to stand as a **320 px rail** on the right, one figure wide, its five cells over the range's machine-time bars, top-aligned and scrolling itself when the six exceed the board. Nothing else moves: the list stays 420 px, the rows and the detail body are unchanged, and under 1400 px the page is byte-identical to the paragraph above. The bars' label and value columns narrow to 72/56 in the rail so the track keeps about 140 px, below which a seven-row chart stops being comparable — which is the only thing the chart is for.

The threshold is 420 + ~600 + 320 + two `--group-gap`, where ~600 px is the width below which the detail's seven-node stage track stops being legible. The 1280 px `.wrap.wide` cap sits under it deliberately, so the rail is reachable only with content width set to full, and there only on a window around 1728 px or wider at 100 % text.

It is a **container query on a measuring wrapper the History page renders around itself** (`.runs-frame`), and both halves of that are load-bearing. A media query is the wrong instrument: the board's width is the window minus the 240 px rail, minus `--body-pad` twice, minus whatever the measure cap is doing, all divided by `.shell`'s `zoom` — at 120 % text a 1920 px window leaves at most 1312 CSS px of board (1600 − 240 − 48), which is not room for three columns and which `@media (min-width: 1920px)` would fill with them anyway. And the container is that wrapper rather than `.wrap` or `.main` because `container-type: inline-size` applies layout containment, which makes the element the containing block for every `position: fixed` descendant: the item modal and the form sheets (§8.7) are fixed and render inside `.wrap` with no portal, so a container up there would pin them to the section instead of the viewport. Nothing under Runs is fixed today; whatever becomes so must portal to `body`. Watchdog renders no wrapper — it has no strip to stand as a rail. The strip and the band are placed through the page's own classes (`.runs-stats`, `.runs-band`) passed to the primitives as `className`, the contract `Sheet` already had (the design spec's §12.1), never by selecting `.ui-figure-strip` from the page.

**The Live sheet.** Title and a subtitle counting its own contents (`3 runs · 1 starting`), then one **row, not a card**, per run whose status is `running` or `paused`, or that is `starting`: a `Dot`, the project at 14/500, `⚠ N` in `--amber` when the run carries attention entries (the deleted `RunStrip.tsx`'s `N needs attention`, compressed to the count and its glyph), the two-tone `1 / 5`, elapsed at 12 `--ink3`, and a status pill only where one is earned — `‖ paused`, `⚠ crashed`, and nothing at all on a running, fresh run, whose state the dot and the elapsed reading already carry.

A launch sent to another machine reads `Starting on <machine>` on the same terms, and the band's line counts them apart as `N launching elsewhere`; a remote run's row carries a machine tag beside its `remote` one.
- A **crashed** run — running, heartbeat stale — is a two-line row: a `--red` dot, a `crashed` pill, and a second line in `--amber` at 12 px carrying `no heartbeat for <age>`, then `last reported <id> at <stage>` or `all items at rest` (`client/src/components/runs/RunsView.tsx:295`), then the clause `watchdogClause` composes (`client/src/lib/run-watchdog.ts:109`). All three readings travel together or the row says less than the strip it replaces did.

Everything C's live card carried that no longer fits a 420 px row — the run id and start clock, the heartbeat word, `$ · N turns · N sessions`, the mode pill, `paused after <id>`, and the current item's stage track — is in the detail sheet, which is beside the list rather than behind a click.

**The History sheet.** Title and subtitle (`28 runs · all`), day kickers at 13/500 `--ink2` in `dayLabel`'s own form (`run-stats.ts:708`), and one **44 px** row per past run: the dot **and** the status word from `runStatusChip` (`client/src/lib/run-stage.ts:268`) — `done` / `aborted` / `failed` / `paused`, toned `--ink3`, `--amber`, `--red` and `--fill-live` — then the project at 14/500, the two-tone count, wall time at 12 `--ink3` and the cost beside it when usage exists. The word is not decoration: a dot alone cannot tell the first three apart, and three colours of the same dot is the encoding §5 rules out. Load-more stays a flat chip at the sheet's foot, in pages of 25. Each row insets its contents **12 px** from the sheet's content box, so the dot clears the row's leading edge and the 2 px selection marker on it, while the row itself keeps the full width and the day kicker keeps the box's own edge — the rows read as indented under the date labelling them. The kicker rests **flush at the scroll box's top edge**: the sheet's top padding is moved inside the scrolled content, because a sticky child of a scroll box otherwise parks at the box's content edge with rows still visible in the padding band above it, and the date then appears to travel across the rows (reported 2026-09-17). A row **selects** the run into the detail sheet — nothing opens. There is no run modal on this page, and none anywhere in this redesign. Live runs are never in this list, and a crashed run is a Live row rather than a History one; a run reaches History when it has finished, not when it has stopped reporting.

**The detail sheet.** One run, whole, beside the list.

Its **head** is the project (a `Dot` plus 19/500), the run id at 12 `--ink3`, the item count when the run is finished, and `RunControls` (`client/src/components/RunControls.tsx:94`) right as 28 px chips — unchanged in what it offers: running and fresh gets **Pause**; #### 8.4.2 Watchdog

**The band.** `Runs · Watchdog`, the `section · destination` convention the tree sets, with `stateLine`'s own sentence (`run-watchdog.ts:154`) as its 13 px subtitle — `armed — watching <ids>, next check in Ns`, `idle — no running run`, `off — <reason>`, each gaining `· resume disabled` when the switch is off. Right, one flat `Policy in Settings ›` chip: the policy is read here and edited there, and a second editor for the same three numbers is a second thing to keep in agreement.

**Three figures.** **Sweeper** — the phase as a 24/700 word rather than a number, since there is no quantity here, with a 6 px sweep meter under it in `--fill-progress` carrying `.hatch` (§8.2) and the line `next sweep in 4m 12s · every 10m`; the meter draws only while armed. **Watching** — the count of running runs over the app's own three counts, `⚠ 1 crashed · 2 fresh · 1 not yet watched`, the last of them drawn only when the runs payload is a tick ahead of the sweeper (`WatchdogMonitor.tsx:193-208`). Those three words are the tile's own and not a paraphrase of them: what a reader needs here is how many runs the sweeper holds an opinion about and how many it does not yet, and a count this tile cannot name is the one thing it must never print. **Policy** — `check every` / `leave alone for` / `give up after` as three label-over-value pairs, 12 over 14/500, with the enabled switch's state as the 12 px line. Both the sweeper line's cadence and all three policy values are the saved config's, not constants; their bounds are `WATCHDOG_LIMITS` (`shared/types.ts:1029`), and the Settings ladders and the server's clamp already read that one triple.

Two switches reach this page and they are not interchangeable, which is why the Policy line names its own — in the mock's words, `resume spawns on · your switch, not the phase`. `WatchdogConfig.enabled` is the user's Settings toggle and withholds the **spawn** alone: a watchdog disabled there still arms, still ticks, and still reports the crashed run it would have resumed. The phase reads `off` only when the environment says so — `offReason()` returns `BM_WATCHDOG off` or `BM_AGENTS off` and nothing else (`server/src/agents/watchdog.service.ts:228-232`, whose own comment records that `enabled` is deliberately not folded in) — and it is that state, an operator's rather than a user's, which hides the Watching sheet below and puts `nothing is watched while off` in this tile.

**The Watching sheet.** One row per run in the runs payload whose status is `running`, annotated from `watching` exactly as today — skew rendered, not hidden. Each row carries a `Dot`, the project at 14/500, the run id at 12 `--ink3`, `· not yet watched` when the payload is a tick ahead of the sweeper (`client/src/components/runs/WatchdogMonitor.tsx:271`), the verdict as glyph plus word (`● ok` / `⚠ crashed`), `last reported <id> · <stage>` or `between items`, and the heartbeat meter — the age against `RUN_STALE_MS` (`shared/types.ts:767`), amber once past it — under its two labels. A crashed row adds the attempts dots, the `watchdogClause` sentence, `→ session <id>`, and `leave alone Nm more` while the grace clock runs. A `Resume now` chip is drawn **only** when `watchdogStoodDown` allows — never while the sweeper will still spawn (attempts left AND, since bug-35, refusals under the same ceiling), whatever the grace clock says, because that is the one function both this chip and §8.4.1's detail head read. A watched id with no run in the payload renders as a placeholder line rather than as nothing: a set the console cannot explain is the failure this page exists to show.

The meter's first label is `heartbeat Ns ago` (`{beat}`, `WatchdogMonitor.tsx:311`) — a numeral every time. Its second label carries none: `stale at <RUN_STALE_MS>` and `past the <RUN_STALE_MS> stale line` are both formatted from the constant at render time (`WatchdogMonitor.tsx:316-318`), and the comment standing beside them gives the reason (`:312-314`): a meter labelled with a typed literal keeps naming the old window the day `RUN_STALE_MS` moves, and on that day the label lies while the meter behind it is still right. The same rule is why this section names the constant instead of its value.

The row is a button, and it **jumps to History and selects the run in its detail sheet** — which is what `WatchdogMonitor` does today (`onSelectRun`, `WatchdogMonitor.tsx:79`), and under option D is the only place it could send anyone: the run's detail *is* that sheet.

**The Activity sheet.** The event ledger keeps today's five columns and full run ids — `time · kind · project · run · what the sweeper did` — with `th` at 12/400 `--ink2`, `td` at 13, and the time column at 12 `--ink3`. Its subtitle keeps the caveat rather than burying it: the last `WATCHDOG_EVENT_CAP` events only (`shared/types.ts:1111`), held in the API process's memory, emptied by a restart. The kind cell is `WATCHDOG_KIND_GLYPH` plus the word, coloured by `WATCHDOG_KIND_TONE` (both `run-watchdog.ts:251` and `:271`) — `live` and `done` in `--green`, `bad` in `--red`, `warn` in `--amber`, `muted` in `--ink3`; seven kinds share those five tones, and the word beside the glyph is always the readable answer. The sheet scrolls inside itself under 700 px rather than letting five columns set the page's width.

**Why it stays a page.** Folding the console into the run rows was drawn twice and picked against both times, and the reason is what the console is for: it is read *during* a run, while the reader is already looking at that run, and its Watching set is the **sweeper's** set — one poll tick of skew away from the runs payload by design. Rendered as annotations on the run rows, that skew would read as the list being wrong; rendered as its own set, with `· not yet watched` on the rows that differ, it reads as the one true fact it is.

### 8.8 Motion

Four places on this board move on their own, and one mechanism covers all four rather than four separate ones:

- The **run chip**'s `Dot` (§8.3) breathes a ring while any run is live — `Dot`'s own `breathe?` flag (the design spec's §12.2, per §8.2's one-home rule) rather than an animation local to `RunChip`, so any other live `Dot` on the board earns the same motion for free.
- The **stage track**'s current node (§8.4.3) pulses the 3 px ring already stated there as one of its four node states; this section is where its behaviour under reduced motion is decided, not where its look is drawn a second time.
- A **needs-you control** fades into place rather than snapping in: the crashed run's `Resume run` (§8.4.1's detail sheet head) and the Watchdog page's `Resume now` (§8.4.2) are gated by the one function, `watchdogStoodDown`, and mean the same thing wherever they appear — the sweeper has given up and a person is the only path left — so both arrive by fading into a slot the layout already reserves rather than shoving the row beside them.
- The **wordmark's cursor** (§8.0) blinks while a run on this machine is working — `.rail-cursor.blink`, the one class `SideRail` adds from `working`.

All four are silenced under `prefers-reduced-motion: reduce` through the same pattern this codebase already uses, not a mechanism written new for this redesign: a blanket `@media (prefers-reduced-motion: reduce)` rule (`client/src/styles.css:728`) cuts every animation's duration to near zero and runs it once, which freezes it on its LAST keyframe rather than cancelling it — wrong whenever that last frame is not the element's resting state. Three elements already needed the fix for exactly that reason: an explicit `animation: none` after the unconditional rule, in whichever reduced-motion block sits nearest it, carrying `!important` whenever that unconditional rule outranks it on specificity. `.board-card-stage-glyph` is the worked example (`:735`): its unconditional rule is `.board-card-stage .board-card-stage-glyph` (`:464`), two classes deep, so plain source order cannot win and the override needs the flag. `.watchdog-lamp-armed` needs it too, in its own block (`:1443`). `.run-track-dot-current` / `.run-track-node[data-in="live"]` need neither: each shares its selector with its own unconditional rule earlier in the same section, so source order alone settles it (`:2180-2181`). The four this section names carry the same explicit override, each judged per selector: `.ui-dot-breathe` (`:2373`), the stage track's `.run-track-dot-current` (`:2181`), `.run-controls-needs-you` (`:877`) and `.rail-cursor.blink` (beside its own rule in the shell section), none of them needing the flag, because each shares its selector with the unconditional rule it corrects and comes after it — a cursor frozen on `opacity: 0` would read as no wordmark at all. `test/motion-style.test.ts` drives all four from one table, and asserts the glyph's `!important` beside them so that "only where it is needed" stays a judgement rather than a habit. (Every line number here is a pointer, not a contract — they move.)

#### 8.9.1 Board

**The fold** (`GroupTop.dc.html`, G-A; grouped-board spec §3). A `jira.json` the server cannot read says so in the card in the Board's own words, never as an empty list. The tile wording `BoardsTen.html` and `NewBoard.html` draw is the mocks' alone.

**Skills.** Phase 5's card, under Connection: `SettingsGroup` titled `Skills`. Two locked rows first — the built-ins' labels (`Work it end to end`, `Open with the ticket loaded`) with a `neutral` `built-in` pill where a skill's `×` sits, no control, because a built-in is code and not a stored row — then one row per skill, its name over the template drawn as a code span (`--steel` fill, 12 px `--ink`, clamped to two lines, the whole text in the `title`; §8.1 allows no second face, so it is the span treatment and not a monospace stack). The `×` asks through `ui/Confirm` inline in its place, one row at a time. The add row stacks a 36 px name field, a `.sheet-prompt` textarea for the template and an `Add` chip, disabled until both hold something after trim; a refusal is the server's sentence in `--red` under it and changes nothing. The hint lists the three placeholders (`{key}`, `{url}`, `{repo}`), says a template without `{key}` gets the ticket key on a line after it, and says a skill has to exist in the repo or the Claude install and that this list only names it. Settings › Local › Dispatch gains `Jira default action` — a `Select` over the two built-ins by label and the skills — drawn only while the status says configured; its hint says the chosen action is listed first in a Jira card's Run menu, marked `default`. A stored skill that has been deleted reads as `Work it end to end` — in the select and in the menu alike — without the stored value being rewritten.

**The board sheet.** `JiraBoardSheet`, `BoardSheet.html` and `NewBoard.html`: `FormSheet`'s third composer (§8.7), one sheet for new and edit — titled `New board` under a `new board` kicker, interval `1m`, `Create board` and no delete for a new one; the board's own name under `edit board`, `Save` and `Delete board` for an edit. Three sections on hairline rules, each a 15/500 title over a 13 px `--ink2` line saying what it is for:

- **Name & sync** — two `SettingsRow`s, the name in the 36 px text field and the interval as a `Segmented` `pill` over `SYNC_INTERVALS`, the control GitHub › Settings' `Sync` card draws for a GitHub repo's interval, so the two read alike.
- **Roots** — one 32 px row per key, the key at 12/500 `--ink2` and a `×`, then a search field whose 420 px `Popover` lists `/api/jira/search` answers (a key already on the board inert, reading `already a root`); a pick adds the key. A row reads the key alone, because only the key is stored, and the mock's `· 7 under it` has no source (spec §1).
- **Queries** — the four chips `+ Assigned to me`, `+ Open in current sprint`, `+ Unresolved in a project…` (which reveals a project `Select` in place) and `+ Custom JQL`, and one row per query: the label, the JQL in a 13 px textarea, and the check line under it — `4 issues match · checked 3 s ago` in `--green`, or Jira's parse message in `--red` with the textarea's stroke `--red` too — checked 500 ms after the last keystroke.

The footer: a 12 px `--ink3` note (`polled right after you create it` / `polled again right after you save`), `Delete board` (`danger`, edit only, asking through `ui/Confirm` inline in its place), `Cancel` (`flat`), and the action (`ink`), disabled with a title until there is a name and at least one root or query, reading `saving…` for as long as the server takes to sweep the saved board (at most 20 s). A refusal keeps the sheet open with every edit where it was and the server's sentence in `--red` under the footer.

**Repositories.** One row per mapped path — the project (`PAY · Payments` on its first row, the bare key on later ones), the path in `~` form, a `×` — then a `--mustard` warning row for each project with issues on some board and no path, in the spec's words (`no repository yet — PAY cards cannot Start until a path is mapped`, spec §1's override of the mock's), then the add row: a project `Select`, a path field and `Add`. Mustard, not red: an unmapped project is a step not taken yet, not a failure. A refusal is shown under the add row in the server's words and changes nothing locally — the card only ever draws what the status says is stored.

**A path's defaults** (Jira repo/branch, spec §5.1). Under the FIRST row of each distinct path — the defaults belong to the path, not to a project, because one checkout can serve two — one wrapping line: a base field (placeholder `e.g. develop`, the path's branches offered as a datalist once the row's one `/refs` read lands), a wider pattern field (placeholder `{key}-{slug}`) and a `Save` chip, posting both values to `/repo-defaults` with an empty field sent as `null` (unset, so the sheet falls back). A pattern `patternProblem` refuses is a hint under the line and never disables `Save` — the server is the judge; a repository the board cannot read says `branches unavailable — <path> <reason>` there, with both fields still usable. A refused save is the server's sentence in the add row's slot and changes nothing.

**A path's worktrees** (M7, the repo/branch final review). Under the same first row, a stacked row: a `worktrees` hint with a `neutral` count `Pill`, then every tree the path has open beside its own checkout (`repoWorktrees`) — ticket or not, detached included — as §8.9.2's own rows (`JiraWorktreeRow`), without the repository column, which is the row above. The card and the modal find a tree by the key its branch carries, so a Continue on `develop` makes a tree neither shows; this list is where it is still seen and its `Remove` still copied. A row a live session's key is on (`treeLiveKey`) is disabled and titled `a session is running on <KEY>`; a key-less tree cannot be tied to a session and keeps the title that says so. `/worktrees` is read on mount and again only when the set of mapped paths or of live keys changes, never on a status reload, and the last answer stays drawn while a re-read is out; a path with no tree, or a failed read, draws no row.

**Connection.** A report of the server's `.env` and nothing to set: `Site`, `Signed in as` (the name Jira gives, never an e-mail; in `--red` with the reason while access is not `ok`), `Token` (`classic` or `scoped`, whose hint names the three scopes a scoped token needs and does not claim to have checked them — spec §1), and `Last sweep` (`every 15 s` or `idle`, `· N calls`, then `· last 429 <age> ago` in `--red` inside 15 min or `· no 429 since start`), closing on `restart the server to change it`, because a control here could only lie.

#### 8.9.4 Chip and the Sources card's Jira row

**The chip.** `JiraChip`, `Trackers.html`: §8.0's tracker chip a second time, on the same `.tracker-chip*` classes — one look, because a second family for the same pill is how two chips come to disagree — drawn after it in the strip, and only while Jira is configured: a 26 px avatar with ONE initial (`?` while Jira has not said who the token belongs to — two letters are the card's reading), a red pip whenever access is not `ok` (no amber state: without credentials there is no chip), `Jira · <first name>` at 12.5/600, and two `Meter`s. `POLL` counts down to the soonest syncing board's next sweep on that board's own interval — `—` with no boards, amber `sync off` when every board is off, `…` before the first sweep, a full amber `overdue` after two silent intervals. `CALLS` is the last tick's spend against `JIRA_SWEEP_CALL_CEILING` (100, the app's yardstick for a lot of calls in one sweep, not Atlassian's limit), green, and red for 15 min after Jira's last 429 (`JIRA_429_RED_MS`) — a window, not a latch. The accessible name is `Jira: <full name>`; the meters ride as its description, as `TrackerChip`'s do (#230).

Its popover is `Popover` at 420 px, a reading with no links and no buttons (the rail rule): the identity over the site, the access phrase in `--red` with its detail when access is not `ok`, one wrapping 13 px line per board — `<name> · polled 12 s ago` and its failure in `--red`, in one column, because a board has no timer of its own to draw and a failure's sentence is the thing the row exists to show — and the sweep's two lines in the tracker popover's API block, worded by the Connection card's own `sweepLine` and `accessPhrase` so the two surfaces cannot word one fact two ways.

Below 700 px the chip moves into the rail bar beside the tracker's, one element in one home as §8.0 says. When both are there, neither draws its meters (§8.0): avatar, pip and caret only, so ☰ keeps its 36 px; a lone Jira chip keeps its meters.

**The Sources card's Jira row.** Settings › Shared › Sources (§8.6) closes on one read-only Jira row in every state — `configured · acme.atlassian.net · 2 boards`, `not configured`, or `checking…` / `unavailable` before Jira has answered — and carries no control: a board's interval is set on Setup's Boards card beside the roots it polls, and a second picker here would be a second writer of one setting. While Jira is configured the card adds a `Jira › Setup ↗` `.set-link` — `onOpenJiraPage('setup')`, the shell's pair threaded down from `App`, never a switch of the card's own — so it opens exactly what the rail's tree entry opens. The old `Trackers` row wrote `Jira › Setup` as text for the rail rule; the threaded pair is what lets a link keep that rule.

#### 8.9.5 Launch sheet

`JiraLaunchSheet` (Jira phase 5; spec §7): `FormSheet`'s fourth composer (§8.7), the one extra tap between a ticket and a running Claude — dispatch edits code in another repository with nobody at a terminal, so this is where the prompt is read before it is sent. It is the board's `LaunchSheet` read for a ticket, and composes the same primitives: scrim, air, 620 px, the shell lift, full-screen under 700 px, §8.6's 36 px controls and the `.sheet-*` field family. The header is a `run` kicker over `<KEY> · <summary>`; the footer is `Copy prompt` (`flat`, 28 px, reading `Copied` for two seconds, absent without a clipboard API) and `Start` (`ink`, reading `starting…` while the request is out). Escape and the scrim are the shell's, and the sheet is hosted once, in `JiraView`, after the modal (§8.7).

The fields, top to bottom: **Action** (a `Select` over the two built-ins by label and the skills by name — seeded from the row picked in the `Run ▾` menu, which is where Settings' `Jira default action` is read — the sheet itself never reads it); **Repository** (the mapped paths in `~` form: a static line when there is one, a `Select` opening on `choose…` when there are several, so the preview waits for a pick rather than guessing); **Prompt** — a read-only `.sheet-prompt` textarea holding the server's own composition (`GET /api/jira/prompt`; the sheet never builds one), or the server's refusal in the `.sheet-blocked` line with Start disabled, or `loading…` / `choose a repository to see the prompt`; **Assign to me** and **Move to**, side by side — a `Switch` and a `Select` opening on `leave as is`, both off, the server applying them BEFORE the spawn — assign, then transition, then the session — so a write that landed stands if the spawn then fails; **Permissions**, **Model** and **Effort** on one row, permissions seeded from the action (`plan` for `context`, `acceptEdits` for `execute`) and clamped to the dashboard's ceiling, model and effort seeded from Settings and never the last launch; and **Remote control**, a `Switch`, for the reason §8's standing rule gives (a raised control marks a state, and this one persists for the session it launches).

**Branch** (Jira repo/branch, spec §5.3, §5.6), under Repository and above Prompt — where the session will work. A `Segmented` of `New` / `Continue` / `No branch`, `No branch` absent for `execute` (an execute with no tree would commit on whatever the mapped checkout holds); each mode keeps its own fields, so flipping away and back returns what was typed. Under it the age of the list, `as of last fetch, N min ago` or `never fetched` (`fetchAgeLine`), at 12 px `--ink3`: the board lists refs and never fetches, so the reader is told how old they are. `New` is a base `Select` (seeded from the path's stored base, else `origin/HEAD`, else the checkout's own branch) and a name field (seeded from the path's pattern); `Continue` is a `Select` grouped `this ticket` (the branches that carry the key) over `other branches`, with the word `behind` or `diverged` beside it (`.sheet-static`, 11 px `--ink2`, titled with what it compares) on one `.jira-branch-line` — the session starts from the local tip, so a stale one is worth a word. A repository the board cannot read swaps the age line for one `.sheet-blocked` line, `branches unavailable — <path> <reason>`, and turns both selects into text fields, because `jira.mjs worktree` re-checks on the host what the board could not. Where the session goes is said only when it is not the obvious place: `will work in <path>` when Continue picks a branch another tree already holds, and `works in the mapped checkout itself — no branch, no worktree` for `No branch` — both `.sheet-note`, every path in `~` form (`displayPath`). A Continue on a branch that carries no key (`continueOffTicket`) is accepted and says one more `.sheet-note`, `this tree won't show on the card — it's listed under the repo in Setup` (M7) — drawn only while no refusal is, so the two sentences never stand together. A draft the server would refuse (`draftRefusal`, the same rules) is said in the `.sheet-blocked` line before Start, and a New name that already exists carries a `switch to Continue` chip on that branch, the server's own remedy. The server's own refusal of the same draft reaches the Prompt field's `.sheet-blocked` line through the preview, and a Start it refuses is §8.9.5's `.sheet-error` alert like any other. For `execute` with a branch, an `Open MR when done` `Switch`, off on every open; with `Continue` and the switch on, a `Target` field opening on `the repository's default`. The choice rides both the preview and Start, so the prompt shown is the prompt sent.

`Start` is the only thing the environment can hide (the rule is [invariants.md](../docs/subsystems/invariants.md#run--on-a-jira-card-is-never-hidden-for-the-dashboards-sake)): none is drawn before the agents status has landed or while the gate says `hidden`, and a `disabled` one carries the first reason that applies as its `title` — `choose a repository`, the dashboard's view of the repository, then the prompt's own refusal. `Copy prompt` waits for the preview and nothing else. A failed Start is the `.sheet-error` `role="alert"` line and the sheet stays open with every field where it was — except when the refusal says the writes stand (`— the assign stands`, `— the Jira writes stand`): the ticket has moved, so the board is reloaded as a landed Start would reload it and `Move to` goes back to `leave as is`, because the fresh read no longer offers that transition; a landed one replaces the form with `started · <session id>`, an `open in dashboard ↗` link and a note that the session's questions appear there — and on the phone, if the dashboard's hooks are installed — and drops the footer, because a second `Start` would be a second session on the same ticket.

It reads `v0.2.0`, or `v0.2.0+3` three commits past the tag, with the kit's accent dot (`--uk-accent`, `--cyan`) while a release newer than the last one this browser opened the drawer on exists. No chip while the checkout has no version. On a phone the board passes `narrow` from `useNarrow()`, which gives the pill the kit's 44 px hit area; nothing around the wrapper may clip it.

The notes go through the kit's own escape-first renderer, so a `###` line reads as a heading. This board owns only the `--uk-*` mapping in `styles.css`: each badge's status word on a 14 % tint of its own token over `--strip` (Feature `--green`, Fix `--amber-ink`, Performance `--cyan`, Breaking `--red`), a code span marked as the item body marks one — `--uk-code-bg` a `--steel` fill and `--uk-font-mono` the board's one face (§8.1), never a monospace — `--uk-z: 80`, and `--uk-zoom` on `--font-scale` so the panel fits the screen at any text size. `test/ui-kit-guard.test.ts` fails on any rule here that restyles a `.uk-*` class or sets a `--uk-*` property that is not one of the kit's public tokens.

### 8.11 GitHub › PRs

GitHub's second page, between Board and Archive in its tree (`GITHUB_PAGES`), and like every source page switched by that tree alone (§8.0). It lists every open pull request of the registered GitHub repos — forks and other authors included — and offers exactly three writes: merge, arm or disarm auto-merge, and update branch (the source-sections spec, Goal 2). It draws in Settings' language rather than a new one: a band, then one card per repo, every look a `ui/` primitive's, and its own `.prs-*` classes only for layout — guard 7 forbids restyling a primitive from here. It scrolls in the well like Settings and reserves no height, so it reads no strip token (§8.0's `--main-gap` has exactly two readers). Every derivation it prints lives in `client/src/lib/prs.ts`, `lib/pr-run.ts` and `lib/pr-layouts.ts`; `PullRequestsView` and the three layouts (`PrInbox`, `PrMatrix`, `PrCards`) place them and decide nothing. The page draws ONE of three layouts — Inbox, Matrix or Cards — over the same rows, and every layout carries everything the page does (the layouts paragraphs below).

**The band.** `Pull requests` over `open pull requests on this machine's GitHub repos`, and a neutral `N open` pill — the sum of each SHOWN repo's `total` (a repo the token cannot read is not counted, see Hidden repos), not of the rows drawn. Before the first answer the page says `loading…`; a failed first read says `pull requests unavailable — <error>`; a failed later read keeps the rows and puts `refresh failed — <error>` above them, because a person part-way through the list should not lose it to one bad poll. A server with no token draws no card at all, only `no token — set BM_GITHUB_TOKEN in .env and restart`: the fix is on the host, so the page says where.

**The toolbar and the layout switch.** Under the band, one row of 14 px gaps that wraps: a `Segmented` (`Layout`: `Inbox`, `Matrix`, `Cards`), then the hidden-repo note when there is one, then the newest `polled N s ago` of the shown repos at the right (`PolledAge`, on its own one-second clock). The choice is stored per device (`PR_LAYOUT_KEY`, `usePersistedState`) and read through `parseLayout`, so an unknown stored word is Inbox, the default. Matrix is wide-only, by `useNarrow` and never a literal of its own: a narrow window DRAWS a stored `matrix` as Inbox (`drawableLayout`) and the switch offers no Matrix (`layoutOptions`), and since a draw never writes the stored word, the choice returns with the window. The loading, `no token`, `pull requests unavailable` and `refresh failed` lines sit where the band's paragraph puts them, above or instead of the toolbar.

**Hidden repos and the empty states.** A repo whose last read was `forbidden` or `not-found` is one the token cannot read (`splitReach`, `isNoAccess`, `lib/pr-layouts.ts`): no layout is ever handed it — even if an earlier read left it rows, they are not rows to act on — and `N open` leaves it out. The toolbar says `N repos hidden — no access · GitHub › Settings`, the last part a `.set-link` button calling `onOpenSettings`, the shell's pair threaded down from `App` the way the Sources card's links are, so the rail's tree stays the only page switch; Settings' `Access` card (§8.6) names them and the fix. A rate-limited or generic `error` repo is transient and is NOT hidden: it stays, with its `detail`. A hidden repo returns on its own with the next read that answers `ok`. Empty states are checked in this order and are the same in every layout: `no GitHub repo registered` tests the payload's repo list, never the shown one; a payload whose every repo is hidden says `no repo this token can read`; shown repos holding no open PR make Inbox and Matrix say `no open pull requests` (Cards keeps its per-repo line). That last sentence is distinct from Inbox's `No pull request at this level.`, which only a selected tile can draw.

**Inbox** (`PrInbox`, the default; the dashboard Git inbox's shape). Three count tiles — `Needs you`, `Worth a look`, `Quiet`, each a `<button aria-pressed>` with the level's `Dot` — that filter; a second click clears. The filter is held as a LEVEL, so a PR a re-read moves out of it simply leaves the list; an empty level's tile stays drawn. Below them every shown PR is ranked across all repos (`rankPrs`: level, then problem severity, then newest update) and drawn by level. A loud item (Needs you, Worth a look) is boxless with a hairline between items: the dot, `#n` link, title at 15/500 and the repo at 13 px `--ink3`; the verdict at 14 px (`prVerdict`: the first problem as a sentence, e.g. `Checks are failing.`); the steps at 13 px `--ink2` under it, the calm ones (the run warning, `Approved.`) a step down at `--ink3`; `author · head → base · age`; and on the right, wrapping under on a narrow window, the compact keys. A Quiet PR is one line — dot, `#n`, title, repo, `quietFacts` in `--ink3` and the run warning as a warn `Pill` — followed by its own `Actions` toggle, a button with `aria-expanded` BESIDE the `#n` link and never wrapping it (a link inside a button is invalid nesting). Shown repos whose last read was `rate-limited` or `error` add a `Can't read` heading and one line each with the `detail`; their PRs stay ranked and actionable, because a failed refresh is no reason to stop offering a merge. Everything is keyed `<repo>#<number>`, never by index (`pr-item-<key>`, `pr-quiet-<key>`, `pr-tile-<level>`, `pr-cantread-<repo>`).

**Compact keys.** `compactKeys` picks, per PR, which of `Merge…`, `Update branch` and `Enable`/`Disable auto-merge` to offer and which is primary (the filled one): `Update branch` when the PR is behind its base, else `Merge…` when the PR is Quiet, not a draft and not blocked; a PR with a problem has no primary, so the verdict, not a bright button, is where the eye lands. `Open ↗` always follows. A disabled key carries its block reason as visible text beside it, never only on hover. `Merge…` does not merge: it swaps the compact keys for the full strip IN PLACE (the item takes the full width and `Open ↗` steps aside, the `#n` link still opens GitHub), where the method is visible and `Confirm` is one click further. A folded quiet strip is unmounted, so its `Confirm` leaves `useDialogEscape`'s stack with it (Escape has one owner).

**Matrix** (`PrMatrix`; wide windows only). A real `<table>` inside `Ledger`'s overflow box (`pr-matrix`), one row per PR in rank order: a dot, the PR (`#n` link and title, a `draft` pill, and a sub-line of `repo · head → base` plus the run warning), then Checks, Review, Mergeable, Base, Auto-merge and Updated. Colour is for failure only: a cell's tone is `ok` and `na` in ink, `bad` and `meh` in the needs-you and worth-a-look tones, `live` for in motion (pending, `computing`, `updating…`), and the cell's word is always its text, so colour is never the only carrier. Each header counts the rows whose cell there is `bad` or `meh` (`columnCounts`). A cell reports its OWN fact whatever the row's level — a draft with failing checks sits among the Quiet rows with a red Checks cell and a counted header, because the dot is the triage and the cells are the evidence; an unnamed `blocked` or `unstable` shows in Mergeable. The whole row (`pr-mrow-<key>`, focusable) toggles ONE expansion (`pr-expand-<key>`) holding the full actions strip and `Open on GitHub ↗`; opening another row replaces it, a click inside an `a`, `button`, `select` or `input` is that control's, and Enter or Space toggles only when the row itself holds focus. The closed expansion is unmounted, for the Escape reason above. A shown repo with a transient failure draws one muted row with its `detail` (`pr-mfail-<repo>`), and a legend (`pr-matrix-legend`) closes the table.

**Cards** (`PrCards`). The page as it was before the layouts, minus the repos the token cannot read: one `RepoSheet` per repo, whose anatomy is described by the paragraphs headed `(Cards)` below (grouping, repo heading, row anatomy).

**What every layout carries.** Nothing the cards show is lost in another layout. The run warning is a warn `Pill` in each; a disabled action's reason is text beside it in each; the method `Select`, the merge `Confirm` and the outcome line are the one `PrActions` and `PrOutcomeLine` in each. The outcome of a write that took the PR off the list (`#n merged`) and each sync-off repo's server sentence are drawn once above Inbox's and Matrix's list, and `<repo>: showing n of total` below it (`PrRepoNotes`, `pr-departed-<key>`, `pr-syncoff-<repo>`, `pr-truncated-<repo>`); Cards says the same in each repo's card. The outcome line of a PR still listed, and its `updating…`, are never inside a collapsed part: Inbox draws them under the item or the quiet line, Matrix as a line beneath the row (outside the expansion) with `updating…` also in the Base cell. A PR's keys stay disabled in every layout while its write runs: the page holds an in-flight set keyed `<repo>#<number>` and passes it down as `busy`, because a fold, a collapse or a layout switch unmounts the strip and with it its own busy state. Outcomes, update marks and the clock are the page's, so switching layout mid-update keeps the mark.

**Grouping (Cards).** One `Sheet` per repo (16 px radius, 24 px padding, `--strip`), stacked with the well's 16 px gap, in `groupRepos` order: repos with open PRs first, the one touched most recently on top, then the empty ones by name; inside a repo the PRs are newest update first. The payload's own order is never what is drawn. A repo is a card of its own, not a kicker over one long list, because what a person can do differs by repo — its merge methods, its auto-merge setting, whether its sync is on — and a card is where that boundary reads.

**The repo heading (Cards).** `SheetHead`, the repo as its 19/500 title. The one-line sub carries the readings, 12 px apart: `polled N s ago` (`pollAge`, the same reading the tracker chip and the Jira board use, on a one-second clock of its own so only that span re-renders), `showing <n> of <total>` when GitHub had more than one page (`truncated`; the page states what it left out rather than paginating), and `no open pull requests` for a repo read successfully with none. A repo whose sync is off puts a warn `sync off` pill in the head's right slot and the server's full sentence (`repo.syncOff`, `syncOffBlock`'s one home, never a client copy) on a 13 px `--ink2` line under the head, once — readable without hover, because a phone has none. A repo whose last read was not `ok` puts its `detail` on the same kind of line in `--red`.

**Row anatomy (Cards).** Boxless rows with a hairline between them, §8.6's settings row turned into a stack, top to bottom: `#<n>` in `--ink2` (a link to the PR on github.com, in a new tab with no referrer, underlined on hover) beside the title at 15/500 `--ink`; the author (`ghost` for a deleted account) and `head → base` at 13 px `--ink2`; the chips; the actions; the outcome line. The chips are `Pill`s in `prChips`' reading order — `draft` neutral; `approved` done, `changes requested` bad, `review required` warn; `checks passing` done, `checks failing` bad, `checks pending` warn; `conflicts` bad; `behind base` warn; `auto-merge · <method>` live — and a repo with no checks or a mergeability GitHub is still computing draws nothing for it, because a chip claims a fact.

**The warning chip.** When something is still working the PR's branch — a live or paused run on this machine or another, a launch pending on another machine, a live claim — `prRunWarning`'s reading (`run in progress on this machine`, `run in progress on <host>`, `launch pending`, `claimed by a live session`) joins the chips as a warn `Pill`. It is a warning and never a refusal: every action keeps exactly the state it would have without it (the spec's "warned about, not refused"). The page derives it from what the Board already polls and adds no request for it.

**Actions and their reasons.** `PrActions`, the one strip every layout draws (`variant="full"` is this one; Inbox's `compact` is a front for it, never a second implementation of a write). One wrapping row, 8/12 px gaps: the method `Select` (the repo's `methods`, seeded by `defaultMethod`, a stale pick falling back to it), `Merge` as an `ink` chip at 28 px, then `Enable auto-merge` or `Disable auto-merge` and `Update branch` as outline chips. A blocked action is disabled AND says why in a 12 px `--ink3` word beside it (`.prs-why`), named as the button's `aria-describedby`; the action and its reason are one inline group, so a wrap never strands a reason under the wrong button. The reasons are `mergeBlock`, `updateBlock` and `autoMergeBlock`, first match wins: `sync off` (the short word on each action of a sync-off repo, since the heading carries the sentence), `draft`, `not mergeable`, `checks failing`, `no merge method allowed`, `fork does not allow edits`, `no permission to update` (GitHub says the PR cannot be updated while it is behind its base), `already up to date`, `auto-merge not enabled on the repo`. `Merge` asks first through `Confirm`, inline in place of the chip — `Merge #<n> into <base> (<method>)?` with a danger `Merge` and a flat `Cancel`, the dismissal focused (§8.4.1's rule); the other two do not ask, because arming is undone by the same control and an update-branch only merges base into head. While a write is in flight every action on its row is disabled until the page's re-read lands, so a second click cannot send a head SHA the first may already have moved.

**The outcome line.** `PrOutcomeLine` (`pr-outcome`, `role="status"`), the one line every layout draws, never inside a collapsed part: one 13 px `--ink2` line under the actions: `outcomeLine`'s word for a write that stood (`merged`, `already merged`, `auto-merge armed`, `auto-merge off`, `no auto-merge was armed`), or the server's refusal sentence verbatim in `--red` — a 409's `Head branch was modified…`, a 502's `the token lacks permission for this — …` — never a paraphrase. Every write re-reads afterwards, success or failure. A merge's re-read takes the PR off the open list, so its line moves to the foot of the repo's card as `#<n> merged` rather than vanishing with the row that earned it.

**`updating…`.** GitHub answers update-branch with a 202 and merges later, so the outcome line reads `updating…` while `isUpdating` holds for the PR: until a read shows a head SHA other than the one the update was asked from, or `UPDATING_MS` (30 s, `shared/types.ts`'s `PR_UPDATING_MS`) pass — and at that moment the page re-reads once, so the row is not left showing a head the update has since moved; the server makes the repo due at that same moment, so the re-read is GitHub's answer and not the cache's 60 s TTL. A read that shows the head moved first ends it early, timer and all.
