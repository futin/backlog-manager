## Critical findings

`Critical | security | server/src/agents/origin.guard.ts:97 | The POST guard has no Host allowlist, so a DNS-rebinding page defeats both of its checks and reaches the session-spawning routes | `sameOrigin` is `new URL(origin).host === host` — a page served from `http://evil.test:4322` rebound to 127.0.0.1 sends `Origin: http://evil.test:4322` with `Host: evil.test:4322` (a match), and its own fetch is same-origin so `content-type: application/json` needs no preflight; `main.ts:24` listens with no host check and `agents.controller.ts:82` forwards the body's `prompt` verbatim to `POST /api/spawn`, giving an arbitrary prompt at the dashboard's permission ceiling`

**Failure scenario.** An attacker gets a victim on this machine to load a page from a domain
they control, served on port 4322. After the page loads, DNS for that domain re-resolves to
127.0.0.1. The page then `fetch`es `/api/agents/dispatch` — the request is same-origin from the
browser's point of view, so no preflight is required and `content-type: application/json` is
sent freely; `Origin` and `Host` both read `evil.test:4322`, so the guard's equality check
passes. The request lands on the local API, which forwards the attacker's `prompt` verbatim to
the dashboard's `POST /api/spawn` at the dashboard's permission ceiling — a Claude Code session
with file-write permission in another repo on this machine.

**Verification note (UPHELD).** Verified at source: origin.guard.ts:97 compares new URL(origin).host against req.headers.host — two headers the attacking page controls together, so a DNS-rebound page on http://evil.test:4322 satisfies the Origin check while its fetch is genuinely same-origin and so sends application/json with no preflight, clearing both of the guard's checks. main.ts:24 is `await app.listen(PORT, BIND)` with no Host validation, no helmet, no host middleware in app.module.ts/security.ts (CSP connect-src 'self' binds the board's own pages, not the attacker's), and agents.controller.ts:82 does forward body.prompt verbatim into AgentsService.dispatch -> POST /api/spawn with permissionMode clamped only to the dashboard ceiling. The documented threat model in docs/invariants.md:1185-1206 and the guard's own header comment scope the design to hidden cross-origin form POSTs and Origin: null only, never mentioning Host validation or rebinding. An unclosed hole in a defense the repo deliberately built, not a restatement of an accepted decision.

The point is narrow and worth stating precisely: loopback binding is not the failure here, and
the origin guard is not useless — it does what its header comment says it does, blocking hidden
cross-origin form POSTs and `Origin: null`. Rebinding is simply a case its threat model never
names, and the standard mitigation (validate `Host` against an allowlist of
`localhost`/`127.0.0.1` plus whatever tailnet name is deliberately served) sits at a layer the
repo has not built yet.
